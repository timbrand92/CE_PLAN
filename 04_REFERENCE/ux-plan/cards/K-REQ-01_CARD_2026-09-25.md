# K-REQ-01 workflow card — CDPROFILE Apply and the Pit Schedule update together

**DRAFT · awaiting Tim's approval before any code starts.** Not built, tested in AutoCAD, installed or
Tim-accepted. Source of the ruling: `decisions/2026-09-25_V3_PLAN_DISCUSSION_RULINGS.md`, "How commands
behave — 25 Sep 2026, 13:18", UX-PROFILE-05 (CDPROFILE PR #187's open decision 5). **Tim: "Both together
now."** The choice read: *The long section and the matching schedule rows update in one step. This needs a
combined preview and one-Undo build first, so it arrives later either way.* Also recorded in
`areas/civil-K-profiles-long-sections.md` item 2 as a **REQUESTED BUILD**, not yet started.

## 1. What works today — Keep / Missing

1. **CDPROFILE itself — Keep.** `Modules/Drainage/Commands/ProfileCommands.cs`, `GenerateProfile()`:
   the drafter picks (or has pre-selected) a starting CE pit, `ProfileRouteEvidenceCaptureService` inspects
   the reachable routes from it, and `CalculationsV2Dialog` opens on a `ProfileRouteReviewViewModel` showing
   the route choice, each pit/pipe node's chainage, cover, invert, depth, diameter, grade, velocity and full
   flow (all read as `Unknown` where CE cannot prove a value), a datum level and horizontal/vertical scale.
   This part of the workflow is unaffected by this card.
2. **Apply already supports updating a previously-placed section — Keep.**
   `Modules/Drainage/Services/LongitudinalSectionService.cs`'s write path carries
   `LinkedSectionWriteResources.ExistingReference` / `ExistingDefinition`, i.e. re-running Apply on a route
   that already has a placed long-section block updates that block rather than always creating a new one.
   This is the "updated" half of "when a long section is updated" in Tim's ruling.
3. **What Apply actually draws — Keep, described accurately.** The written block is a graphic: layers for
   linework, pit markers, surface, value/heading/title text and a pit-marker block with a `PIT_ID`
   attribute, laid out at chosen horizontal/vertical scale with a title, boundary and pit bars. It reads
   pit/pipe evidence current at the moment Apply runs; it does not itself change any pit or pipe's cover,
   invert or depth — CDPROFILE is a review-and-draw tool over data that already exists on other CE objects
   (pipes and pits), not a levels editor.
4. **Pit Schedule is a fully separate command and window — Missing the connection.**
   `Modules/Drainage/Commands/PitScheduleCommand.cs`'s `PITSCHEDULE` opens `PitScheduleDialog` with no
   argument and no relationship to whatever CDPROFILE last did; its own code comment says opening it is
   "deliberately geometry-safe," i.e. it reads the drawing itself, independently, whenever a drafter opens
   it. There is no code path from `ProfileCommands`/`LongitudinalSectionService` into
   `PitScheduleCommand`/`PitScheduleDialog` or vice versa. **This confirms the area file's own record:**
   "Until it is built, the schedule is not refreshed by CDPROFILE (nothing silent is added in the
   meantime)" (`areas/civil-K-profiles-long-sections.md`, item 2). So today: if a drafter has the Pit
   Schedule open in one window and runs CDPROFILE Apply that changes what the schedule ought to show (for
   the pits on that route), the open schedule window does not update; the drafter has to close and reopen
   `PITSCHEDULE` to see current values. If the schedule is closed the whole time, the next open will read
   current data anyway — so the real gap is a **live/open schedule going stale**, and the **lack of one
   shared preview and one Undo** across both outputs, not a data-correctness bug in a freshly-opened
   schedule.
5. **PR #187's other open decisions — for context, not this card.** Decisions 1, 2, 3 and 4 were settled 25
   Sep (kept, Older calculators, CR-A3 rounding, any-CE-user-approves). Decision 6 ("one Review home") is
   also now closed — **UX-REV-01: "One Project Review (Recommended)"** — one Project Review window from the
   CE tab covering Civil and Structural checks, calculations, profiles and proposals. This card does not
   depend on decision 6 and does not attempt it; it is noted here only so a builder does not re-open it by
   mistake.

## 2. The full experience — today's state and the intended result

1. **Ribbon/trigger — Keep, unchanged.** CDPROFILE stays reachable exactly as it is (Review panel, compact,
   as **Profile** per the design pack). No new command name.
2. **Prompts — Keep, unchanged.** The starting-pit pick (or pre-selection) is unaffected.
3. **Selection — Keep, unchanged.**
4. **Preview — Missing, this is the build.** Today Apply's own preview (inside `CalculationsV2Dialog`, via
   `ApplyCommand`/`CanApply`/`HasReadyPreview` on `ProfileRouteReviewViewModel`) shows only the long-section
   diagram that is about to be drawn or updated. Intended: the same preview also lists which Pit Schedule
   rows (by pit ID) belong to the route being drawn, and what would change in each — cover, invert, depth,
   or nothing, if the schedule already agrees with the drawing. One preview, both outputs, before anything
   is written.
5. **Drawing output — Modify.** Today Apply writes only the long-section block. Intended: the same Apply
   also refreshes the Pit Schedule's stored/displayed rows for the pits on that route to match what the
   section just drew, in the same operation — not a second command, not a silent background write between
   commands.
6. **Cancel — Keep the existing rule, extend its scope.** Cancelling the CDPROFILE review leaves the
   drawing untouched today; intended: it leaves both the section and the schedule untouched, since neither
   has been written yet.
7. **Escape — Keep, unchanged**, same extension of scope as Cancel.
8. **One Undo — Missing, the core of the ruling.** Today, Apply's own write is presumably one Undo already
   (a `LongitudinalSectionWriteReceipt` from one write pass); intended: **one Undo reverses the section
   update and every Pit Schedule row change together.** No partial state where the section moved forward
   but the schedule did not, or the reverse.
9. **Save/reopen — Modify.** Today reopening `PITSCHEDULE` after a CDPROFILE Apply already shows current
   data, because it reads the drawing fresh on open (§1.4). Intended: this stays true, and in addition an
   already-open schedule window (if the UI supports one staying open across commands) reflects the same
   update immediately rather than needing a manual reopen. If Pit Schedule is not normally left open across
   other commands in practice, this point may be moot — flagged as OPEN 2 below.
10. **Where values come from — Keep, unchanged.** Cover/invert/depth/diameter/grade continue to come from
    the pipe/pit objects themselves, per the existing evidence model; this card does not introduce a new
    value source, only a second, simultaneous place those same values are written to (the schedule display)
    alongside the section drawing.

## 3. Example drawings

1. **DWG-A or DWG-B (Civil):** a job with an existing CDPROFILE long section already placed for one pipe
   run, and the Pit Schedule already generated for the same job, where at least one pit on that run has had
   its invert or cover changed on the drawing since the section/schedule were last generated (e.g. by an
   ordinary pipe/pit edit). This is the exact scenario the combined-update build needs to prove: both
   outputs disagree with the drawing before the test, and agree with each other and the drawing after one
   Apply.

## 4. Automated guards vs Tim's AutoCAD checklist

1. **Automated:** a test that changes a pit's invert on a synthetic drawing, runs the equivalent of
   CDPROFILE Apply programmatically, and asserts both the long-section block's node text and the Pit
   Schedule's stored row for that pit now agree with the new invert; a test asserting one Undo (one
   transaction / one `UndoRecord`) reverses both; a test asserting Cancel/Escape before Apply leaves both
   the section block and the schedule rows exactly as they were.
2. **Tim's AutoCAD checklist (DWG-A or DWG-B):** change one pit's cover or invert on the drawing directly
   (an ordinary pit edit, not through CDPROFILE). Run CDPROFILE on the route containing that pit and press
   Apply. **Right result:** the preview named both the section change and the affected schedule row before
   Apply; after Apply, the redrawn section and the Pit Schedule (reopened if it was already open) show the
   same new value; one Undo removes both changes and the drawing and schedule display return to the
   pre-Apply state exactly.

## 5. Slices — smallest first

1. **Slice 1 — read-only combined preview.** Extend `ProfileRouteReviewViewModel`'s preview to also compute
   and display which Pit Schedule rows the current route touches and what would change in each, without
   writing anything yet. Proves the pit-to-schedule-row mapping is correct before any write logic is built.
2. **Slice 2 — combined write, one Undo, single route.** Wire Apply so that accepting the preview writes the
   section block (as today) and the affected schedule rows in the same transaction/Undo group, for the
   simple case of one route with no ambiguous or Unknown pit matches.
3. **Slice 3 — the edge cases.** A pit on the route that the schedule does not currently list at all (e.g.
   added to the drawing after the schedule was last generated); a pit whose schedule row was manually
   overridden/pinned by a drafter (must not be silently overwritten — surfaced in the preview instead, per
   the standing "manual value stays marked manual" rule); Cancel/Escape at every stage confirmed to leave
   both outputs untouched.

## 6. OPEN questions, each with a recommended answer

1. **OPEN 1 — when a pit on the route has a manually overridden/pinned Pit Schedule value (per UX-SCHED-01's
   "a DEPTH typed in the Pit Schedule updates the pit, with preview"), does CDPROFILE's combined Apply
   overwrite that pinned value, or does it surface the conflict in the preview for the drafter to choose?**
   *Recommended: surface it in the preview, never silently overwrite a value a drafter deliberately typed —
   consistent with the standing rule that every value is editable and marked manual, and with UX-SCHED-01's
   own preview-first pattern for schedule writes.*
2. **OPEN 2 — is the Pit Schedule ever genuinely left open in the background while a drafter runs other
   commands including CDPROFILE, or is it always opened, read, closed?** This changes whether "the open
   window updates live" is real scope or a non-issue. *Recommended: build for "closed, then reopened shows
   correct data" first (already true today per §1.4); treat "stays open and refreshes live while CDPROFILE
   runs" as a nice-to-have only if Tim confirms drafters actually work that way.*
3. **OPEN 3 — does the combined Apply also need to reach the long-section's own instruction/heading line,
   which the standing no-retirement rule already protects (decision 1, kept)?** *Recommended: no — decision
   1 is settled and out of scope; this card only adds the Pit Schedule side of the write.*
