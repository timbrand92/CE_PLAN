## ANSWER FIRST

### FOR TIM

1. **My own mistakes first: none that cost anything.** I ran the full Civil test suite at about 08:45, inside your drafting hours: it took 4 minutes 36 seconds at low priority, with AutoCAD not running on the robot side.
2. **The cause, in drawing terms:** CE keeps one copy of the job's pits and pipes in memory. At the start of a command it only asked "is this the same file name as before?". When you close a drawing without saving and open the same file again, the name matches, so CE kept the OLD drawing's copy and never read the reopened drawing's own one.
3. **Why it then refused DP and OF:** at the click, CE copies each pipe's ID tag from the pipe line into its records and saves them. The old copy already had them, so nothing was saved into the reopened drawing. The final safety check then re-read the drawing, found the pipes without their ID tags, filled them in half-way through its own reading and refused because "the drawing changed while I was reading it".
4. **Why it needed a placement first:** the first DP is what tied CE's copy to that file name. With nothing placed in the first drawing, the copy was only tied at the reopened drawing's first DP, which reads the drawing properly. That matches the robot exactly (8 of 8 refused after a placement, 2 of 2 fine without one, waiting 60 seconds changes nothing).
5. **The fix (draft PR #1830):** when a drawing closes, CE now notes in its memory that its copy belonged to a drawing that has gone. The next CE command in a drawing with the same name reads that drawing's own copy, exactly as the first command in any newly opened drawing already does. Nothing is written to the drawing that is closing, and nothing touches REDO.
6. **What changes for a drafter:** DP, OF and the other downpipe-type sources place normally after you close a drawing without saving and open it again. The CE log gets one new line: "[BUG-1225] ... was opened again after its drawing closed; CE loads this drawing's own record."
7. **A second gain (from reading the code, not seen in a run):** before this fix, any CE command in the reopened drawing could save the closed drawing's copy into it, for example a downpipe you had thrown away by not saving. That can no longer happen once the drawing has closed.
8. **There is an on/off switch, ON by default** because it fixes a fault: `reopenedDrawingLoadsItsOwnRecord` in the `linking` group of `%APPDATA%\TIM_CE_CADTOOLS\CD_Settings.json`. Off brings back the old behaviour.
9. **The robot cases that prove it** once a build with #1830 is installed: N13 (DP) run straight after N13a, and N14 (OF) straight after N14a, each pair in one AutoCAD session (`C:\Lisp Files\_ACAD_DRIVER\cases\`). Right looks like "Downpipe placed. Tag: DP" and "Overflow placed. Tag: OF" both times, with no "could not be refreshed" on the command line or in the CE log.
10. **Nothing for you to do now.** Built and unit-tested only. Nobody has opened it in AutoCAD.

## Summary (under 100 words)

BUG-1225 cause found with confidence: `SetDrawingPath` kept CE's in-memory pit and pipe record whenever the file name matched, so after a close and reopen of the same file the closed drawing's record stayed; identities copied at the first pick never reached the reopened drawing, and the final landing check refused. Fix in draft PR #1830: the drawing-closing handler marks the record (memory only) and the next command loads the drawing's own record; switch `linking.reopenedDrawingLoadsItsOwnRecord` ON. 17 new tests; Civil net10 20677 passed, 0 failed; net48 compiles. Robot proof: N13 and N14.
