1. **S04-01 — HIGH — Network redesign propagates the far end's IL as the next pit's outlet level. VERIFIED-BY-READING.**

   **File:line:** `Modules/Drainage/Services/NetworkDesignService.cs:329`, `:333`, `:348`, `:352`, `:356`. The faulty check is `Modules/Drainage/Services/NetworkRedesignSolverService.OutputValidation.cs:188` through `:194` (the comparison of the pipe's downstream IL with its upstream pit). Production call: `Modules/Drainage/Services/NetworkRedesignSolverService.cs:232` and `:246`.

   **What happens in AutoCAD:** The Network redesign preview can approve a gravity run with a rise through an intermediate pit, even while each individual pipe falls correctly. A drafter sees plausible pipe grades, but the arriving pipe sits below the departing pipe. The proposed pit IL/depth is wrong as well. A correct existing run is not required to contain any pre-existing backfall to trigger this.

   **Exact failure:** Processing moves upstream from the nominated outlet. For pipe U-to-D, the code correctly calculates `pipeUpstreamIL = pipeDownstreamIL + length / gradeRatio`, then incorrectly stores `pitInvert[U] = pipeDownstreamIL`. The next incoming pipe is anchored to that remote level plus the 0.030 m junction drop, rather than U's actual outgoing start level. For B-to-C, 20 m at 1:100 into C at RL 10.000 gives B's departing end RL 10.200, but stores pit B at 10.000. A-to-B therefore arrives at 10.030, 170 mm below B's outlet.

   **Why the existing check misses it:** The per-pipe revalidation at `NetworkDesignService.cs:513` checks each pipe separately. The redesign output check compares `pipe.DownstreamInvertM` with `upstreamPit.InvertM`, repeating the same end mismatch. It does not test arriving versus departing levels at the junction. Thus this fixture is not rejected by the calculation validation.

   **Live route and write evidence:** `CivilHubService.cs:157` builds the pipeline; the complete preview feeds the apply ticket. `NetworkRedesignApplyTicketService.cs:338` copies proposed pit ILs, and `:361` copies proposed pipe ILs. `NetworkRedesignApplyCoordinator.cs:186` calls the real drawing writer. `LinkService.NetworkRedesignApply.cs:337` through `:368` writes these pipe end values to linked records and invert annotations. There is no correction of the junction arithmetic on that path. The preview itself is the minimum sufficient AutoCAD oracle; native Apply remains to be exercised by the authorised test lane.

   **DETERMINISTIC TEST — fixture:** Prepare a synthetic, saved Civil model-space DWG with three ordinary CE pits A (0,0), B (20000,0), C (40000,0), all cover RL 12.000. Use two straight, correctly linked DN150 UPVC gravity pipes A-to-B and B-to-C, each 20 m. Existing pit ILs: A 10.600, B 10.300, C 10.000. Existing pipe ILs: A-to-B 10.600/10.300; B-to-C 10.300/10.000. These initially match their pits, deliberately avoiding S04-02. Include each pipe's linked main label, both invert labels and flow arrow; include an up-to-date placed CE pit schedule with its matching saved baseline, no manual overrides, unique identities, unlocked layers and no Xrefs. C is an ordinary nominated outlet, not a Fixed CDLPD boundary.

   **Fixture Settings:** In the isolated profile, DN150 minimum grade 1:100, minimum velocity 0.6 m/s, maximum velocity 6 m/s, UPVC Manning n 0.010, minimum cover 300 mm, no maximum cover. Preserve the drawn DN150 sizes. These values make the supplied 5 and 10 L/s flows feasible at 1:100, so no unrelated infeasibility hides the fault.

   **Typed/click steps:** Type `CDHUB`; click `Network redesign`, `Designing from scratch`, `Select network on plan` and pick the connected A-B-C network. Use `Select top controls` for A. Use `Current` and `Proposed LPD` to select C for both roles. Click C's `Assign branch pits` and select A, B, C. Click `4 · Enter local inflows`: enter A=5, B=5, C=0 according to the named prompts. Click `5 · Confirm outlet ILs`, enter C=10.000; choose no loop break. Click `Build read-only preview`.

   **Assertion:** Read the proposed pipe IL columns and final schedule. At B, A-to-B's arriving IL must be B-to-C's departing IL plus 0.030 m. With the stated fixture, correct values are B departure 10.200, A arrival at B 10.230 and A upstream 10.430. The audited code instead produces A-to-B 10.230/10.030 and B-to-C 10.200/10.000, with pit A 10.030 and pit B 10.000. Assert the preview never presents that 170 mm rise as an acceptable solved run. For later native write confirmation on a disposable copy, tick the approval checkbox and click `Apply approved redesign`; inspect the two IL labels at B and the schedule, then one U. The calculation regression must check cross-pit continuity using the actual upstream end, not reproduce the faulty downstream-to-upstream-pit comparison.

   **Correction direction:** Carry each pit's actual outgoing start IL upstream, then add the nominated junction drop for incoming pipes. Independently validate every junction and derive pit levels from their own physical ends. Fixing only the assertion or only the preview wording leaves wrong engineering values.

2. **S04-02 — MEDIUM — a real pit drop is mistaken for a drawing change, so Network redesign cannot be applied. VERIFIED-BY-READING.**

   **File:line:** `Modules/Drainage/Services/NetworkRedesignPreviewService.Projection.cs:197` and `:199`; source pit value `Modules/Drainage/Services/NetworkRedesignDrawingProjector.cs:305`; rejection `Modules/Drainage/Services/NetworkRedesignApplyTicketService.cs:472` through `:480`. UI gate: `Modules/Drainage/ViewModels/NetworkRedesignHubViewModel.cs:318`.

   **What happens in AutoCAD:** With an ordinary drop between an inlet and outlet, the pipe's “before” IL in the preview is replaced by the pit floor IL. Apply is disabled and the window says that pipe's levels changed after the preview evidence was created. Rebuilding the preview cannot fix it because nothing actually changed.

   **Exact failure:** The preview gets `ExistingUpstreamInvertM` and `ExistingDownstreamInvertM` from the two `NetworkRedesignCurrentNodeEvidence` records. Those records hold `PitData.InvertLevel`, not `PipeData.FromInvert/ToInvert`. The apply ticket compares these substituted numbers with the actual pipe fields using a 0.0000005 m tolerance. Any genuine pipe-end offset from the pit IL exceeds that tolerance. The reject reason is therefore deterministic, including on a newly rebuilt preview. This is independent of S04-01's proposed-level arithmetic.

   **DETERMINISTIC TEST — fixture:** Use a fresh copy of S04-01 before its proposed changes. Keep B's floor and departing B-to-C end at RL 10.300. Set only the arriving A-to-B end at B to RL 10.330, consistently in the actual pipe, its linked data, project record and invert annotation. Leave A-to-B upstream at 10.600; refresh the fixture's placed schedule and saved baseline before the test. No manual invert override flags, no locked layers. This gives a legitimate 30 mm drop at B.

   **Typed/click steps:** Perform the same `CDHUB` Network redesign selections and local flow/outlet entries as S04-01, then `Build read-only preview`. Read A-to-B's existing/downstream IL, the reason list and `Apply approved redesign`. Click `Check again` without editing the drawing.

   **Assertion:** The “before” downstream IL for A-to-B must be 10.330, not B's pit IL 10.300. The window must not say `Pipe '<A-to-B row label>' levels changed after the preview evidence was created.` The audited source substitutes 10.300, emits that exact reason with the displayed pipe label, and sets `CanApply=false`; Check again repeats it. Also assert the saved A-to-B downstream IL remains 10.330. After repair, a genuinely modified pipe after preview must still be detected; do not remove the stale-data check to make this test pass.

   **Correction direction:** Freeze and display the actual current pipe-end ILs separately from pit levels. Compare each current pipe field against that same field's captured value. Preserve a legitimate pit drop and the existing stale-preview protection.

3. **S04-03 — MEDIUM — Run Solve cannot solve its own inputs and falsely reports that every invert already matches. VERIFIED-BY-READING.**

   **File:line:** In-scope contract `Modules/Drainage/Services/PipeSizingSolver.cs:62` and `Modules/Drainage/Services/NetworkDesignService.cs:257`, `:281`, `:289`. Caller mismatch `Modules/Drainage/Services/ProposalApplyService.PlanBuilders.cs:555`; rejected rows discarded at `:72`; false AutoCAD message `Modules/Drainage/Commands/RunSolveCommand.cs:176` through `:179`.

   **What happens in AutoCAD:** Type CDRUNSOLVE on a valid connected run and it can finish without opening a proposal or changing a level. It tells the drafter every invert already matches the solved design. In fact it did not solve any pipe. This is a direct command message, separate from the already audited command-outcome logger.

   **Exact failure:** `BuildRunInputs` assigns literal `CatchmentFlowLps: 0.0` to every node, regardless of any catchment data. Cumulative flow therefore remains zero everywhere. `PipeSizingSolver.TrySize` rejects every request with “Design flow must be greater than zero”. `BuildRunSolvePlan` excludes every infeasible pipe and retains its warnings, leaving zero effective changes but no errors. RunSolveCommand checks only errors and change count, so prints its “every invert already matches” sentence and returns before showing any of those warnings. Existing tests of the solver with positive supplied flow, or of a pre-built feasible plan, cannot exercise this composition.

   **DETERMINISTIC TEST — fixture:** Saved millimetre Civil DWG with ordinary pit A (0,0), pit C (20000,0), both cover RL 12.000; A pit IL 10.600 and C pit IL 10.000. One correctly linked straight DN150 UPVC gravity pipe A-to-C with actual/current end ILs 10.600/10.000, labels and arrow matching. No Fixed/existing pipe, no LPD marker, no locked layer, no overrides. Use the isolated Settings from S04-01. The deliberately steep existing pipe makes it easy to distinguish “a genuine proposed design exists” from “nothing was calculated”.

   **Typed steps:** Type `CDRUNSOLVE`; select pit A at the start-pit prompt; select pit C at the downstream-end prompt. Capture the command line, window appearances and both saved pipe ILs.

   **Assertion:** The command must produce a real proposal or explicitly state the missing-flow/cannot-solve reason. It must not assert the levels already match a solved design. Current source prints `[CDRUNSOLVE] A: run of 1 pipe(s): every invert already matches the solved design - nothing to apply.`, opens no proposal window, and leaves pipe ILs at 10.600/10.000. A later regression should call the real `BuildRunInputs -> Design -> BuildRunSolvePlan` chain and assert zero-flow rejection cannot become “already matches”. Do not inject positive flow directly into a hand-made NetworkInputs and call that a test of CDRUNSOLVE.

   **Correction direction:** Give Run Solve the confirmed inputs its solver requires, or use an explicitly defined level-only calculation where that is the intended task. Surface missing input and infeasibility honestly; zero effective changes does not prove equality. Do not invent a flow or add an engineering hard block to ordinary drafting.
