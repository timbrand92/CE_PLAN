## FIX FIRST

1. **A changed pipe still counts as confirmed (card condition 4 is half met).** The card: "If the LPD or its pipe changes, it counts as not confirmed." The build treats only three changes as "changed": the LPD moved to another pipe end (`Rules\LpdStartPointRule.cs` 115-116; CDLPD drops the old yes, `Services\LpdService.cs` 208 calling `LpdStartPointService.cs` 263-278), the pipe erased, or the pit erased (`LpdStartPointRule.cs` 110-111; `LpdStartPointService.cs` 92-94). Not caught:
   1. **The LPD's pipe edited but kept** (re-joined to another pit, its ends moved, drawn the other way). The pit the tools start from and the name the solver stops at are worked out afresh every run from the LPD record and CE's pipe record (`LpdStartPointService.cs` 118-160), and the confirmation is never compared with what the drafter was shown ("the pipe leaving P1"). So a tool can start from a different pit than the one confirmed, with no question.
   2. **The LPD set again on the same pipe end with a different pit or target.** The older record's own name is built from the drawing, pipe, end, pit and target (installed `MultiLpdAuthorityService.Legacy.cs` 114-120), so a changed pit changes the name; but the build then falls back to matching by pipe end alone (`LpdStartPointRule.cs` 141-152) and finds the old yes. The builder's reason for that fallback ("the older record's name is worked out afresh with Save As") is not proven: the name uses AutoCAD's drawing fingerprint, and the newer record already refuses a different fingerprint (installed `MultiLpdDrawingAuthorityReader.cs` 135-145), which would break every Design-window job saved under a new name if Save As changed it. Robot step: read the fingerprint before and after a Save As on a copy.
   3. **Suggested fix (DRAFT default for Tim):** keep in the item the pit it was confirmed against (its permanent name in the drawing, not a position) and count a different start pit, or a different stop name for the solver, as "the LPD was changed since it was confirmed"; drop the pipe-end fallback unless the robot shows the fingerprint changes on Save As. A test with a re-joined pipe must fail on today's head. The card's wording "on this pipe end, on this date" then needs "from this pit" added.
2. **Two LPDs: asked twice, then the answer is not used, and the solver says "not confirmed".** The question loop asks about every unconfirmed LPD (`LpdStartPointService.cs` 344-366). With two confirmed, CDRENUMBER and the solver both take nothing (`LpdStartPointRule.cs` 247-262), so CDRENUMBER asks its "which pit is the main outlet" question as today, and the solver falls back to the pit-name search and prints "LPD found by pit name at ..., not confirmed" (`Commands\RunSolveCommand.cs` 267) straight after the drafter confirmed both. The PR lists two-LPD use as not built, which is honest; asking a question whose answer does nothing is not. Fix: on a job with more than one LPD, ask nothing until a tool can use the answer and say one plain line instead (for example "two LPDs in this drawing: CE does not yet know which pits drain to each, so the order is worked out as before"), and never call the pit-name find "not confirmed" when LPDs are confirmed. Card robot case 3 cannot pass as written; the controller should mark it "not built".
3. **The long section already uses the stored LPD, unconfirmed.** The PR and change log say the long section "is unchanged: it asks for its starting pit as today". True, but incomplete: installed CDPROFILE's route finder already reads the LPD through the same one reader and stops its routes at the LPD's pit whether or not anyone confirmed it (installed `Services\ProfileRouteEvidenceCaptureService.cs` 187-196 and 1080-1086). So after this step, a stored LPD is "only a proposal" in CDRENUMBER and the solver, and a fact in the long section. Correct the PR and the change log, and put it to the controller as a card line (the card names the long section as a reader but says nothing about this).

## Checked and sound (by reading the code at `6a899344`)

1. **No new store of the LPD itself.** The only new drawing item is `LPD_CONFIRMED` in the existing LPD group (`Services\LpdStorageContract.cs` 16-20). It holds the LPD's name, the pipe's permanent name, the end (0 or 1) and the day, in a versioned list (`LpdStartPointRule.cs` 36-42, 188-195); a test pins exactly those four fields (`LpdStartPointTests.cs` 88-104). It is written only beside an LPD that exists (`LpdStartPointService.cs` 300-305) and never opens either LPD record (227-256).
2. **No position; no tool reads it instead of the LPD.** Every value a tool uses comes from the LPD record through the one reader (`LpdStartPointService.cs` 74-97); the item only filters which recorded LPDs count (`LpdStartPointRule.cs` 236-241). A compiled-plugin test shows only the start-point service loads the item's name (`LpdStartPointTests.cs` 120-131).
3. **The installed strict readers still read both forms as healthy.** The installed reader takes the two records by name (installed `MultiLpdDrawingAuthorityReader.cs` 246-256, 265-266), so the two strict JSON reads (155-164, and `MultiLpdAuthorityService.Json.cs` 92-98) only ever see those two records' text, which this build never changes. The only other code that walks CE's dictionaries skips everything but CE's record and spine (installed `LinkService.SourceChangeCapture.cs` 229-231). Installed CDLPDRESET leaves the LPD group in place when the item is in it (installed `LpdService.cs` 361-367); this build then says "an LPD was confirmed here but none is stored now" and uses nothing (`LpdStartPointRule.cs` 321-327; test 183-197).
4. **Stale when the LPD moves, or its pipe or pit is erased, or CDLPDRESET clears it** (`LpdService.cs` 208 and 368; `LpdStartPointService.cs` 263-292). A Design-window outlet moved to another pipe end asks again (pipe and end compared, `LpdStartPointRule.cs` 116).
5. **Save As to a new job: as the card says.** A copy whose old network was erased shows "the LPD's pipe is no longer in the drawing" (test 270-284). Worth Tim knowing: a new job made by Save As that keeps the old outlet pipe keeps "LPD confirmed" with no question (card 2.4 accepts this for revisions).
6. **Esc carries on in today's way with a warning and stores nothing.** Esc or No returns "not yes" (`LpdStartPointService.cs` 379-388); one line "CE: LPD not confirmed, order may differ." (360-364); nothing stored; the tool continues. Enter alone does not confirm. Worth knowing: after No, the question comes back on every run until Yes.
7. **Read-only drawing.** Nothing is written; the yes is used for the session and CE says so (`LpdStartPointService.cs` 391-413).
8. **Nothing promises one U.** No new line on screen mentions Undo (searched every new quoted string). The yes is stored in its own step inside the tool's command (`LpdStartPointService.cs` 295-313), so one U after the tool should take the yes away together with whatever the tool did; not tried.
9. **CDRENUMBER and CDRUNSOLVE really read the one reader.** Both call `ForTool` (`Commands\PitRenumberCommand.cs` 50; `RunSolveCommand.cs` 247), which reads through `LpdService.ReadLpdAuthoritySet` (`LpdStartPointService.cs` 74), the installed one-reader entry (installed `LpdService.ReadCompatibility.cs` 121-124). The solver's pit-name search now runs only when no LPD is confirmed and says "found by pit name, not confirmed" (`RunSolveCommand.cs` 258-268). The long section: see FIX FIRST 3.
10. **The Pit Schedule is not stopped.** Not touched by this step; it reads the LPD through the same reader (installed `PitScheduleBuilder.cs` 1296), which cannot see the item. The new "LPD needs checking" item in Check Current Drawing only adds to the list; nothing gates on it.
11. **CDLPD's plain reason uses the same rule as its own later refusal** (`LpdService.EvaluateLegacyWriterGuard`, installed `LpdService.ReadCompatibility.cs` 343-390, used by the writers), so nothing that works today is stopped earlier (`Commands\LpdCommand.cs` 40 and 544). The words are plain.
12. **One outlet pipe:** CDRENUMBER follows the pipe records as today and says so when the confirmed LPD is elsewhere (`PitRenumberCommand.cs` 73-79); listed as a DRAFT default.
13. **Merge `6a899344` is clean:** its net change against step 6's head is exactly the own commit's 14 files.
