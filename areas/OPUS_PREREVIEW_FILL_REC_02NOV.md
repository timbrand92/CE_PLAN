### #1419, BUG-803: CDREBUILD treats an original with an out-of-date stored handle as the original

1. **What changes for the drafter.** After WBLOCK or INSERT plus EXPLODE (every object gets a new handle), CDREBUILD now keeps each pit's and pipe's number, key and pipe list and only corrects the stored handle, instead of giving every pit a new ID and clearing its pipe list (`LinkService.CloneRepair.cs`, `RepairStaleClones`, the new `handleOnly` path; rule in `Rules/StaleCloneIdentityRule.cs`). An object counts as the original only when its stored handle names nothing live, no other object carries the same stored handle, and no other pit or pipe carries its spine key (`StaleCloneIdentityRule.Classify`). That is what BUG-803 asks ("the only carrier of an ID keeps it").
2. **Settings switch.** `linking.rebuildKeepsOnlyCarrierIdentity`, default ON. OFF = `Classify` returns Copy for everyone and the `handleOnly` list stays empty, so the old copy path runs unchanged (`StaleCloneIdentityRule.Enabled && clones.Count > 0`). The PR pins `new LinkingSettings()` only; the train's C-64 and later defaults tests carry the key (17 files mention it on the tip). No engineering value hard-coded.
3. **No hard blocks.** None. A failed object is logged and counted in the report (`report.Errors++`), the rest carry on.
4. **Native protection, REDO.**
   1. Opens objects ForWrite in a normal command transaction, as before. An object on a locked layer throws on open and is counted as an error, the same as the old copy path; it is not unlocked. Model space only, so Xref content is never touched. Not a protected file.
   2. Kept pipes keep their explicit From/To pit ids (`LinkService.Utilities.cs`, `keepExplicitPitIds`); a copy still loses them. The handle map leaves out every copy's stored handle so a kept pit is never pointed at an unrelated live object (`BuildHandleMap`, Opus review fix).
   3. `clones` and `carriers` are filled in step (each `clones.Add` is followed by its `carriers.Add` in the same branch), so `verdicts[i]` matches `clones[i]`. Checked.
5. **Risk, said by the author and still open:** a pit pasted from ANOTHER drawing whose stored handle names nothing here now keeps that drawing's ID. If this drawing has its own P5 with a different spine key, CDREBUILD can leave two P5s. Before, the pasted pit got a new number. I could not find whether the paste-time copy handling (deep-clone) already fixes pasted pits before CDREBUILD ever sees them; if it does, the risk is small. Robot scenario below.
6. **Tests.** 13 tests: pure rule cases, the handle map, three source guards, the default. Author reports 2 of 5 failed before. The real `RepairStaleClones` against a drawing is not run headless.
7. **NOT proven, and the robot scenario.** Never driven. Robot: (a) WBLOCK a three-pit, two-pipe network, INSERT and EXPLODE it into a blank drawing, CDREBUILD: P1 to P3 keep their numbers and each pit still lists its pipes. (b) INSERT and EXPLODE the same block twice: both sets become copies with new numbers. (c) COPYCLIP a P5 from job A, PASTECLIP into job B that has its own P5, CDREBUILD: record whether two P5s result. Twin with the switch OFF: every object renumbered (old behaviour).
8. **Verdict: KEEP-WITH-NOTE.** Train class: none needed (in Civil 3.0.74). Note = scenario (c) must be run; if two P5s appear, a carpark item to treat a carrier whose number already exists in the drawing as a copy. Close the GitHub page as merged.
