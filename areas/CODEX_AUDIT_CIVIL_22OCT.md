**ANSWER FIRST — independent Civil + Manager audit, 22 October 2026, Melbourne**

1. **Counts: HIGH 2 / MEDIUM 4 / LOW 1.** Six findings are verified by reading the audited source. One, the meaning of the command-outcome log, remains suspected until its AutoCAD events are recorded. None was tested in AutoCAD in this audit.

2. **Most important: a command that says it changed nothing actually writes to the drawing.** Even with Ignore switched OFF, typing CDCHECKIGNORE creates or rewrites CE's active-drawing record before checking the switch. Its initialisation can also save the project record. Tidy Labels uses the same writing initialisation before its preview or cancellation.

3. **Another serious fault: ignored warnings can stay hidden after the design changes.** The remembered state omits information needed by the check: the pit and clearance values for pipe-to-pit fit, and the actual/required layer for wrong-layer findings.

4. **REDO and DP1:** BUG-861's intermittent loss of REDO remains unexplained by this reading; the suspect paths and a controlled retest are listed below. The empty-selection failure in #1520 is confirmed in the source and the supplied evidence, but is already known and is not counted again.

1. **HIGH — disabled Ignore and cancelled/preview-only Tidy Labels write drawing records. Verified-by-reading.** PR #1517, `Modules/Drainage/Commands/CheckIgnoreCommand.cs:36`; shared initialisation `Commands/CeCommandBase.cs:29` and `:43`; writer `Services/ProjectDataService.Persistence.cs:754`, `:787`, `:808`, `:1301`. Related inherited path reached by #1513: `Commands/TidyLabelsCommand.cs:35`.

   **What happens in AutoCAD:** a drafter can type a disabled command, or answer No to moving labels, and still acquire a changed drawing and a CE database write. A stale project record can also be synchronised before the user agrees to Ignore anything. The words “Nothing was changed” cannot be trusted here.

   **Exact failure:** `InitServicesFull(document)` executes before `AllowIgnoreFinding` at line 38. `InitServices` calls `MarkDrawingActive`, which opens the named-object dictionary for write and writes `CE_CVL_SUITE_PROJECT/PROJECT_ACTIVE = "1"`. There is no equality/no-op guard: an existing Xrecord also receives `existing.Data = data`. `SetDrawingPath` can immediately save records at `ProjectDataService.Mutations.cs:175–179`; full sync can remove stale records and call `SaveProjectData` at `ProjectDataService.cs:376–380`. All precede the switch check and every prompt. The marker alone proves the defect without needing a stale record. Tidy Labels also calls `InitServices` before its switch, selection, count pass and Yes/No decision. These helpers predate C-57; #1517 newly calls them on its claimed no-change route. #1513 inherits the Tidy Labels route.

   **DETERMINISTIC TEST:** fixture A is a saved, empty metric drawing with discipline Unknown, no CE project dictionary, Inspector closed, and `checks.allowIgnoreFinding=false` (also test an absent key, whose class default is false). Capture the named-object dictionary before running the command. Type `CDCHECKIGNORE`. Assert the exact line `Ignoring a finding is switched off in CE Settings. Nothing was changed.` AND assert the dictionary still has no `CE_CVL_SUITE_PROJECT`. The current code fails the second assertion by adding `PROJECT_ACTIVE`. Record DBMOD and the next U description as additional evidence, not the sole oracle. Fixture B has one CE pipe P1-P2 and a movable clashing label; snapshot its project Xrecords and subscribe to ObjectModified on those Xrecords. Type `CDTIDYLABELS`, All, then No. Assert no marker/project write event occurred, not merely that label positions match. Repeat with Escape. For stale-data coverage, seed one orphan pit record with no matching block and verify that disabled Ignore leaves that record byte-for-byte unchanged.

   **Correction direction:** gate disabled commands before any drawing initialisation; use the existing detached/read-only readers for prompts and preview. Enter writing initialisation only after an accepted action. A new check should inspect dictionary writes, not just entity count or ignored-list contents.

2. **HIGH — Ignore does not remember all facts that its warnings depend on. Verified-by-reading.** PR #1517 activates this existing helper; #1511/#1512 add a newly affected row family. `Commands/CheckIgnoreCommand.cs:121`; `Services/Checks/ChecksResult.cs:228–235` and `:288–296`; `Services/Checks/IgnoredChecks.cs:198–228`, `:235–263`; actual fit inputs `Services/PipePitFitReviewService.cs:36–69`.

   **What happens in AutoCAD:** a warning accepted for a particular pit/pipe arrangement can remain hidden after the pit becomes smaller or the required clearance changes. A pit moved from one wrong layer to another can likewise remain silently ignored.

   **Exact failure:** a fit row's key contains pipe AND pit handles, but only the pipe handle is supplied as `TargetRef`; `SecondRef` and `ValueUsed` are empty. `IgnoreFingerprint.ForRow` does not parse the key. Once it matches that pipe, it never includes the pit. It also omits the fit-opening evidence, accepted pit fit geometry and clearance Settings used by `Review`. Changing those inputs can therefore leave the hash identical. For wrong-layer rows the hash includes selected pit dimensions/levels/position, but neither the actual layer nor the office layer; both rows with the same handle/rule have the same key and empty value. The displayed finding text is not hashed. `Evaluate` at `IgnoredChecks.cs:143–149` then classifies the changed warning as StillIgnored, and `ChecksListPaletteService.cs:107–109` removes it from view.

   **DETERMINISTIC TEST — fit:** prepare a synthetic accepted-evidence fixture: pit P3, clear X/Y 600 mm, base RL 0.000 m, lid underside RL 2.000 m; one connected pipe with outside diameter 700 mm, inside diameter 650 mm, wall 25 mm, invert RL 0.500 m, crown RL 1.175 m, outside bottom RL 0.475 m, north wall, centred offset 0. Confirmed fixture clearance source, wall/edge/pipe clearances 50 mm and evidence tolerance 1 mm. Keep a second endpoint available so the pipe record is valid. Enable Ignore and the Checks list. Type `CDCHECKIGNORE`, Ignore, the P3 fit row number, `3`, Enter for note. `CDCHECKS` should now mark that row ignored. In the fixture's second state change only P3's accepted clear X from 600 to 400 mm; preserve handles and the pipe record. Check again. Assert that the fit row returns with `Asked again`, and is absent from HiddenKeys. Current code produces the same fingerprint and keeps it hidden. Independently repeat by changing only the clearance value, retaining a failing fit. The pure regression must build the row through `ChecksResult.Build`, not hand-construct a corrected row with a second reference.

   **DETERMINISTIC TEST — layer:** fixture P3 on layer `AUDIT-WRONG-A`, office pit layer different, `layerChecks.wrongLayerRows=true`. Ignore its wrong-layer finding with reason Other. Use AutoCAD Properties to move P3 to `AUDIT-WRONG-B`, without changing its size, location or levels. Run `CDCHECKS`. Assert the wrong-layer row returns and names `AUDIT-WRONG-B`; current hash logic keeps it ignored. Repeat after changing only the required office layer in the test Settings. Restore test Settings after each run.

   **Correction direction:** fingerprint each finding's actual dependencies, including both fit participants, accepted fit evidence, relevant rule values and layer facts. Do not treat the navigation target as a complete list of engineering dependencies.

3. **MEDIUM — a finding that returns as “Asked again” cannot be ignored again directly. Verified-by-reading.** PR #1517, `Commands/CheckIgnoreCommand.cs:86`; `Services/Checks/IgnoreFindingPicker.cs:18–27`; contrast `Services/Checks/IgnoredChecks.cs:151–158` and `:112–114`.

   **What happens in AutoCAD:** the Checks window asks the drafter to reconsider a changed item, but the Ignore command does not offer that item. The drafter must first find its old entry under Unignore, then run Ignore again.

   **Exact failure:** candidates exclude every key in the saved history, not just keys still hidden after fingerprint evaluation. An AskedAgain record remains in that history by design. The underlying store can replace the old record, but the command never lets that row reach it.

   **DETERMINISTIC TEST:** use P3's wrong-layer fixture above. Ignore the wrong-layer row. Run `CDCHECKS` and verify the P3 row returns as Asked again. Type `CDCHECKIGNORE`, Ignore. Assert P3's wrong-layer row is offered and can receive a new reason/date. Current code excludes it. As a control, Unignore the old P3 entry, then rerun Ignore: the row is offered. Assert this direct route without relying on the total number of unrelated findings.

   **Correction direction:** derive excluded keys from the current IgnoreEvaluation.HiddenKeys, while retaining the historical entry until a new decision is accepted.

4. **MEDIUM — leader-out planning makes room using a plain label that will not actually move. Verified-by-reading.** PR #1513, `Services/LinkService.TextClashTidyUp.cs:426–437`; `Rules/TidyLeaderOutRule.cs:90–126` and `:135–141`.

   **What happens in AutoCAD:** Tidy Labels can move a callout onto a plain label while reporting that it found clear space. The plain label is correctly left alone because CE cannot add its missing leader; the callout was planned on the assumption that the plain label had gone.

   **Exact failure:** Rescue processes all eligible labels and updates its `placed` obstacle map for each leader-out result. Only afterwards does `SplitByLeaderSupport` reject plain-text moves. The rejected text is not restored to the obstacle map and later moves are not revalidated against its real position. Unit tests of Rescue alone and of the split alone miss the contradiction between them.

   **DETERMINISTIC TEST:** use the real `PlanWithLeaderOut` composition with millimetre units, step/max 125 mm, rearrangeNeighbours=false. Ordered items are plain label A with box (0,0)–(100,100), and callout B with box (50,-125)–(150,-25). Both movable; each has only the zero-displacement usual candidate. Fixed obstacles are (0,0)–(10,10) and (140,-120)–(150,-110); no pipe obstacles. Only B is in calloutHandles. Reading the loop gives A a virtual move (0,+125), then B (0,+125). The split keeps only B. Apply only returned moves to the original boxes: B finishes at (50,0)–(150,100), overlapping unchanged A. Assert final moved boxes do not clash with held boxes; current composition fails. For native confirmation, reproduce those measured text boxes/blocked usual positions in a synthetic pipe fixture, type `CDTIDYLABELS`, Select that pipe, Yes; assert the MLeader text extents do not intersect A, A remains unchanged, and one U restores the callout. No such fixture was built or run in this audit.

   **Correction direction:** decide which labels can move before reserving their new positions, or re-plan after rejecting unsupported moves. Validate the final applied set, not the hypothetical rescue set.

5. **MEDIUM — tidy-up checks obstacles in the wrong space, and its search does not expand with the new leader-out distance. Verified-by-reading.** PR #1513 exposes the distance mismatch; the ModelSpace-only scanner is inherited. `Commands/TidyLabelsCommand.cs:169–176`; `Services/LinkService.TextClashTidyUp.cs:28`, `:425`, `:579–605`, `:616–628`, `:725–747`.

   **What happens in AutoCAD:** a paper-space pipe is selected from its layout, but its labels are checked against model-space text. They can be moved because of text on a different space, or fail to avoid text on their own sheet. A longer configured leader-out move can also be approved without reading text at the destination.

   **Exact failure:** PickPipes filters by the current layout, while ScanNearby always enumerates `BlockTableRecord.ModelSpace`. Separately, the scan/filter margin is fixed at `2 * 275 + 1000 = 1550` drawing units. The new rescue uses configurable `TidyLeaderOutMaxMm`, converted to drawing units. No maximum ties that setting to the scanned envelope. In a millimetre drawing with a 3000 mm rescue limit, obstacles outside the 1550 mm scan margin are unavailable to the planner. This is distinct from the previously reviewed conversion of the rescue step/max and from the already-known old candidate unit issue.

   **DETERMINISTIC TEST — spaces:** prepare a synthetic DWG with one CE pipe and its attachments owned by Layout1's paper-space block record. Label B has no clashes on that sheet. Put model-space MTEXT `MODEL ONLY` at B's same numerical XY extents. In Layout1, PS command, type `CDTIDYLABELS`, All. Assert B is not offered for movement. Then remove the model-space text, place `SHEET OBSTACLE` across B in Layout1 and rerun; assert the clash is detected. Before pressing Yes, inspect the preview text and the fixture's owner block-record IDs. This checks actual space ownership, not viewport appearance.

   **DETERMINISTIC TEST — reach:** in a millimetre model-space fixture set leader-out max 3000 mm and step 125 mm. B's text box is (0,0)–(100,100), and the pipe/attachment envelope has maximum Y=100, so the scan stops at Y=1650. Block every usual candidate and all eight rescue positions on every ring through 1500 mm, using small obstacles inside the scan. Leave the north candidate at 1625 mm otherwise clear. Put MTEXT `OUTER OBSTACLE` at measured extents (0,1700)–(100,1710): outside the scan, but inside B's north candidate box (0,1625)–(100,1725). Keep other selected pipes out of the fixture so they cannot enlarge the scan. Type `CDTIDYLABELS`, Select the fixture pipe, Yes. Assert B is held or moved to a genuinely clear position and does not overlap OUTER OBSTACLE. Also assert the scanner includes that obstacle. Current scan excludes it and accepts the north candidate. Restore the configured distance afterwards.

   **Correction direction:** scan the selected pipe's owning space and cover every proposed destination, including its text extents, before accepting a move.

6. **MEDIUM — “completed” in the outcome log is not evidence that a CE action succeeded. Suspected native manifestation; event-only implementation verified-by-reading.** PR #1507, `Services/CommandOutcomeLogService.cs:48–52`, `:76`, `:180–192`; example normal returns `Commands/SourceTagCommand.cs:153–155`, `:165–166`, `:177–197`; caught failure `Commands/CheckIgnoreCommand.cs:65–69`.

   **What happens in AutoCAD:** a cancelled window or a failure that CE catches can be reported as a completed command. A watcher using that line to decide whether a tool worked would receive a false success signal.

   **Exact failure mechanism:** the logger maps AutoCAD CommandEnded directly to completed, CommandCancelled to cancelled and CommandFailed to failed. It receives no result from CE's commands. Those commands routinely handle PromptStatus.Cancel by returning, handle a window Cancel by returning, and catch failures without rethrowing. Nothing tells this logger which happened. Whether each particular route emits CommandEnded in the native host was not observed here, so this remains a suspected runtime finding rather than a claimed reproduction. Merely ending an AutoCAD command can legitimately be called “completed”; the defect is treating this event as the promised action outcome.

   **DETERMINISTIC TEST:** empty synthetic drawing already designated Civil, outcome logging ON. Type `CDTAG`, then Escape at `Pick the source to label:`. Record the actual event name and the resulting CE log line. Assert the action is classified cancelled/no-change, not successful. Second case: in the P3 Ignore fixture, use a debugger exception injection immediately before the drawing writer at CheckIgnoreCommand line 127, so its catch prints `CE could not change the ignored findings. Nothing was changed.` Record CommandEnded/Failed and the outcome line; assert it is not `Command outcome: CDCHECKIGNORE completed ...` presented as success. Do not infer this from the logger's isolated Ended/Failed unit tests. Record both native versions' event sequences.

   **Correction direction:** either label these lines explicitly as native command-lifecycle events, or let commands supply their semantic result. Keep log writing separate from the drawing; no database write was found in the new outcome service itself.

7. **LOW — the new progress ticker is bypassed when the one Checks list is enabled. Verified-by-reading.** PR #1514, `Commands/CheckCurrentDrawingCommand.cs:28–33`; `Commands/ChecksListCommand.cs:53–65`; `Services/ChecksListPaletteService.cs:98–99`; `Services/CurrentDrawingCheckService.cs:43–46`.

   **Exact failure:** TryOpenInstead returns before BuildProgressTicker is called. The routed list calls CheckWithShared, which calls CheckCore without a ticker. This is not the earlier review's question about whether AutoCAD repaints the command line: no progress callback exists on this route at all.

   **DETERMINISTIC TEST:** 10,000-entity synthetic model drawing; `checks.showProgressWhenSlow=true`, `checks.progressAfterSeconds=0.5`. In a debugger, pause ReadObservation at CurrentDrawingCheckService line 260 for two seconds after the legacy route has created its stopwatch, then continue. 2. **Inspector after a pick.** `InspectorPaletteService.cs:647–705` debounces the pick. Its automatic refresh asks the REDO guard at `:1120`; `:1179–1180` excludes project sync while that guard holds. The newer Civil Properties route starts an open-close read at `:820`. This is a real write-capable path, but the inspected normal post-U route has a guard. It is not proof that this path ran unguarded in BUG-861.

3. **Inspector at open/activation.** `:459–471` attaches, considers auto-show and requests an automatic refresh. The one-off discovery at `:522–565` checks command state and REDO before sync. It marks the database discovered before the attempt, so the log and actual saved-record state are needed when investigating a failed first scan; a missing later repeat alone does not prove success. Explicit palette actions/NotifyDataChanged call full refresh without the automatic flag; the inspected external callers are edit/apply routes, not the normal plain-pick observer.

4. **Automatic QA and Xrefs.** `CivilProjectQaAutomaticService.cs:416–452` checks safety and defers at `:423` before session capture. Capture can use ordinary transactions; it is not sufficient to check only for ForWrite. `PitScheduleXrefWatcherAutoCadAdapter.cs:109` and `CivilBackgroundXrefNoticeService.cs:88` also defer through the REDO guard. No new selection-time database writer was introduced by #1511/#1512's pit-layer reader: it uses the caller's read transaction. Errors in that reader become a could-not-check entry.

5. **Real first-open writers.** `PitBlockMigrationService.cs:156–171` defers for REDO, then locks the document and migrates/redefines pit blocks; its migration uses ordinary transactions (`:298`, `:337`) and definition writes (`:346`). `NativeObjects/PipeObjectUpgradeOnOpenService.cs:108–114` similarly defers before calling the pipe upgrade. These are intentional write-capable first-open tasks, not mere presentation refreshes. Their guards and timing must be included in the first-open reproduction.

6. **Project-data cache and persistence.** Link registration warms caches at `LinkService.cs:1597–1617`; cache routines have ordinary/open-close variants. `ProjectDataService.Persistence.cs:502–515` is now only idle-save bookkeeping and does not itself perform the pending write. Actual saving at `:576`/`:1099–1126` writes the named-object dictionary; sync can request it. `SetDrawingPath` can also try to save the previously active drawing (`ProjectDataService.Mutations.cs:175–179`), so a two-document trace must identify which database receives each write. An outer lock on the active document does not establish a lock on that previous document.

7. **Guard lifecycle risk to measure.** `RedoWindowGuard.cs:237–254` closes its remembered hold on every CommandWillStart; `:224–230` does not restore an earlier hold after a cancelled command. The policy assumes the next command ends the protected interval. A single pick normally is not that event, but a native/context-menu command that starts and then cancels could release deferred work. This is a hypothesis to test, not the established cause of BUG-861. Default hold is 0; an explicitly positive hold expires by design. Tim's actual saved hold value was not read here.

10. **What to record for that protocol.** Native command start/end/cancel names; guard open/closed transitions with database identity; first-open migration/upgrade starts; Inspector/QA resume times; every ordinary transaction start and project/marker/definition write, with its initiating method; any SetSystemVariable call. Record the actual order, including whether a write occurred before or after the pick. Use debugger breakpoints or a deliberately reviewed test build in the later test lane. The existing “waiting QA/Inspector refresh” lines prove deferral only, not what eventually invalidated REDO. No safe attribution of BUG-861 can be made from those lines alone.

**Summary**

Seven findings: two HIGH, four MEDIUM and one LOW. The clearest defect is a database write before disabled Ignore or Tidy preview can say no. Ignore also misses essential change dependencies. Tidy planning can approve collisions, returned findings cannot be ignored directly, outcome semantics need native proof, and shared Checks bypass progress. DP1's empty-selection failure is already known. BUG-861 remains open with a concrete trace protocol. No source was changed and no tests were run.
