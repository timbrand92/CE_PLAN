# Structural two-floor ordinary-job walkthrough

**Planning-only fictional scenario.** This joins existing daily cards without inventing engineering values. A mark, size, source or detail remains Manual/Unknown until supplied and reviewed. **Proposed** describes a reviewable handoff, not a built interaction.

| Step | Ordinary drawing action | Handoff / retained boundary |
|---|---|---|
| 1. Start blank job drawing | Open a blank Structural drawing and establish its drawing/layout/view and **Level 1** identity through the existing recognised-context route. | Context is shown in direct prompts/transient preview, not a compulsory wizard. A second visible mark on another floor is not the same identity. Project/issue record remains root-owned. |
| 2. Establish host, then place foundation work | A blank drawing cannot enter host-bound child placement from the two named source files. Stop at the separate **Proposed/owner decision** host-establishment doorway; after a deliberately established host is confirmed, prepare the ordinary route for one host-bound item and one standalone footing item. Only supplied inputs that can derive a complete compound reach the confirming native click; a required Unknown stays visible and the draft can be Parked/Cancelled. | A local Xref edge is evidence only. [Raft host entry/adoption](structural_raft_host_entry_adoption_card.md) names `FADOPT`, its source conflict, and the separate **Proposed** Draw-boundary/Select-existing-outline → confirmed-host-registration doorway; bounded source still lacks a blank-perimeter creation route. Host MOVE later rechecks affected children without regenerating or resetting authored labels. [Foundation card](structural_foundation_first_placement_card.md) governs. |
| 3. Frame Level 1 | Start the retained `1 Regular` route for an explicit beam line, then a selected support route. The final native placement click accepts the visible beam/support result; support links need actual footprint contact and confirmation. | A crossing line is not a link. Support **Edit this only** retains mismatch/review; **Edit together** previews only stated confirmed endpoint links. [Beam](structural_beam_placement_daily_card.md) and [supports/bracing](structural_supports_bracing_daily_card.md) govern. |

| 6. Detail and section | Select a local member for a detail, or use explicit Manual creation. | 9. Selective revision | Edit the changed Level 1 beam/support relationship using **this only** or explicitly previewed **together** scope. Recheck the linked label, detail and schedule row as separate receipts. | **Seam not established:** the approved cards require review of these receipts, but do not establish a built cross-tool transaction that updates all of them together. Park/refresh each affected draft; do not auto-catch up. |
| 10. Finish drawing work | Use direct annotation/joint/centreline tools where needed; revision cloud remains markup evidence only. Save/issue stays outside this walkthrough. | Applied-in-open-drawing, saved/reopened, issue and Tim acceptance are separate states. No step here issues a sheet. |

## Fictitious before/after

Before: a blank Level 1 plan and a blank Level 2 view. After **only once the separate host-establishment doorway has been owner-reviewed**: each has its own explicitly placed local framing/foundation compounds, retained manual label positions, one member-linked detail or Manual detail, and a schedule view with separate Level 1/Level 2 provenance plus visible Parked/Unknown-floor count. A later markup change revises one selected Level 1 relationship without altering the Level 2 lookalike, unrelated labels or issued output.

## Dependency and readiness reconciliation

This is a planning read of the existing cards only. **Ready** means the next card has a reviewable entry, not that a command is Built, Tested, Installed or Tim-accepted.

| Job handoff | Required before this step | Readiness result and no-circular-dependency check |
|---|---|---|
| Recognised drawing → Level/view context | Actual local drawing plus identified drawing/layout/view/level. | **Ready in planning.** Automatic recognised context guides the job; ambiguous context remains unresolved rather than becoming a different job. It does not require a host, schedule or issue first. |
| Blank drawing → first raft host | A deliberate local candidate outline, required known values and separate explicit host registration. | **Concrete open doorway:** only the proposed Draw-boundary / Select-existing-outline → Confirm host-registration route provides this. `FADOPT` remains legacy adoption, never a shortcut. This is a missing owner capability, not a circular dependency or a reason to infer a host. |
| Confirmed host → host-bound foundation child | One explicitly confirmed host plus that child’s own driver/governing inputs sufficient for a complete compound. | **Conditionally ready.** Required Unknown parks the child; it cannot be filled by a schedule, detail or nearby geometry. Standalone footing work follows its own card. An unregistered outline blocks only host-bound work in this scenario. |
| Local framing/support → detail | An explicitly selected actual member, or the separately visible Manual creation entry. | **Ready in planning without a completed schedule.** Detail does not wait for schedule output, and Manual does not fabricate a member identity. Required detail inputs remain visible/Unknown and Park rather than creating a circular “detail needs schedule; schedule needs detail” loop. |
| Selected members/candidate rows → schedule view | Explicit member/row scope with source/provenance and any Unknown/Manual state visible. | **Ready in planning without a completed detail.** The schedule is a coordinated view, not an authority for member/detail inputs. Unknown rows are deliberately Parked/Excluded for this selected output, never silently removed or resolved. |
| Revised local drawing → shared issue review | Selected Structural drawing/layout/sheet identities, affected source/revision/manual state and the shared QA/issue review boundary. | **Root-owned handoff, not an additional Structural prerequisite.** A changed member marks only affected detail/schedule drafts Needs review; it does not auto-update them. The shared issue workflow presents included versus revised sheets and QA disposition for the relevant user/engineer to confirm; the software owner does not decide job revision intent. This planner neither generates an issue nor treats a PDF/export as issue completion. |

**Result.** No new circular dependency was found in this reviewed chain. The only first-use gap identified here is the already-recorded **Proposed** blank-job host-registration interface: it is a documented planning door, still unimplemented/unapproved rather than an established capability. A host-bound child with Required Unknown is a deliberate Park state; it does not block unrelated reviewable framing/detail/schedule work, and it never authorises a substitute host, value, detail or issue output.
