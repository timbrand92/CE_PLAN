## FOR TIM (plain English)

1. **What Codex is, in one picture.** Codex is a programmer that can (a) run commands and scripts on this PC (PowerShell, dotnet, git: it has full access here), and (b) optionally "use the computer" like a person: look at one window, read its list of buttons and boxes, click, double-click, right-click, type. The second part is a separate add-on called Computer Use. We have been using Codex almost only as the second thing, a person clicking screens, which is its weakest and flakiest mode.
2. **Why half the runs fail to start (found today).** The Computer Use add-on works through a small helper program inside each Codex session (called `node_repl`). In the failed runs the helper simply was NOT attached to the session: the add-on's instructions were visible but the helper tool was missing (proved in the saved logs of the 16:31, 20:49 and 20:50 runs; present in the 18:26 and 20:55 runs). Codex then writes "native screen tools unavailable". It is not the screen locking (the PC was logged in and unlocked), not our briefs, and not the model. Three probes run while another Codex test was running also found the helper missing, so it may only be available to one session at a time. The desk will test that when the PC is quiet.
3. **Why Codex also "types into the wrong place".** The add-on sends keystrokes to a window; if the AutoCAD drawing area has the focus instead of the command line, typed text becomes AutoCAD shortcuts (Ctrl+V = paste, so every line became PASTECLIP). That is a focus problem the machine can solve exactly; an AI looking at pictures cannot do it reliably.
4. **What Codex does well and we under-use.** Writing and running scripts, reading logs, comparing files, reviewing code, and judging a window from its picture or from its text list of controls. It can also write its answer as a strict data file (so a result is PASS/FAIL data, not a long essay).
5. **What the testing should be.** A machine runs the tests (fixed scripts, exact mouse positions worked out from the drawing itself, window contents read as text), the same way every time. Codex's job is smaller and better: write and review the test scripts, and look at what only a person can judge (does this window look right), using the window's own text list where possible.
6. **A cost we found on the way.** Each Codex run saves every screenshot inside its own log: 100 to 175 MB per run. The logs now take **28.6 GB of the C: drive** (721 files; 547 are our headless test runs = 21.5 GB). This is why C: keeps filling. Deleting the old headless-run logs would free about 21 GB. That needs your yes (decision below).
7. **Two things I cannot do for you.** Microsoft Defender may be interfering with Codex (the Codex health check says its exclusions are not verified); adding exclusions is a security setting, so it is yours. And a newer Codex is available (CLI 0.163.0, desktop 26.1016): updating it could change behaviour mid-week, so the desk will update only after the weekend run, unless you say otherwise.

## Technical findings

1. **Codex surface (CLI 0.159.2, Windows, model gpt-6.1-sol).** `codex exec` is the headless mode used by `queue3.sh`: prompt in, final message out; `--json` event stream (thread.started, turn.completed, turn.failed, error), `--output-schema <file>` (final answer must match a JSON Schema), `-o <file>`, `--ephemeral` (no session file), `resume`, `--sandbox read-only|workspace-write|danger-full-access`. Our runner uses `--dangerously-bypass-approvals-and-sandbox`, so Codex has full shell, file and network access. Exit codes and failure semantics are not documented (a run that cannot start still exits 0: see queue.log).
2. **Computer Use is a JavaScript API, not a built-in tool.** In a session the skill "computer-use" says: run JavaScript in `node_repl`, `import("@oai/sky")`, then `sky.list_apps()`, `sky.get_window()`, `sky.get_window_state({window, include_screenshot, include_text})` which returns the window's accessibility tree as text with element indexes, and the actions `click` (by element index OR by window-relative pixel + screenshotId; `click_count` for double-click; `mouse_button` right/middle), `press_key`, `type_text`, `set_value`, `scroll`, `drag`, `perform_secondary_action`, `activate_window`, `paste`. It uses SendInput + UI Automation, and screenshots a WINDOW with Windows.Graphics.Capture (works even when occluded). Foreground input on Windows (it takes over the mouse; the user cannot work meanwhile). Docs: `...\@oai\sky\docs\skills\oai_sky_lib\windows\SKILL.md`.
3. **The start failure.** Failed sessions (16:25, 16:31, 20:49, 20:50): the computer-use skill text is in the prompt (2 mentions) but `node_repl` has 0 references and `@oai/sky` 0; working sessions (18:26, 20:55): `node_repl` 255 and 389 references. So the failure is "node_repl not attached", at session start. Failures came in clusters (16:25 to 16:31, 20:49 to 20:50). A fresh probe session (`codex exec`, no tool call, "ATTACHED or MISSING") answered MISSING three times in a row at 21:43 while the 20:55 run was still alive; stale helper processes exist (`codex-computer-use.exe` pid 65936 since 18 Oct; Codex desktop/app-server since 15 Oct; `codex exec-server --remote` since 17 Oct). Not yet proved: one-session-at-a-time exclusivity, stale-helper effect, or sandbox-service start-up effect. The experiment: when no Codex run is active, probe 5 times; kill the stale 18 Oct helper; probe 5 times; probe after a 10 minute idle. Cheap (about 0.1 percent of the week).
4. **Desk fix, built now:** `launch_codex_retry.ps1` runs an ATTACH PROBE before every real run (a 10-second `codex exec --ephemeral`, final line ATTACHED or MISSING) and launches the real run only after ATTACHED (probe every 45 seconds, up to 25 minutes); every probe is logged to `desk_jobs\codex_attach_log.csv` (time, result, helper process count, minutes since the last Codex run) so the cause can be read from data.
5. **What Sky gives us that the briefs ignore:** the accessibility TEXT of a WPF window (names, values, enabled state, element indexes) is available without reading a screenshot: a window look can assert text (Tag box value, button names, clipped or missing rows show as missing elements) deterministically. Briefs should ask for `include_text: true` and quote the tree, and use screenshots only for appearance (pale heading, clipping, colour). Briefs should also use window-relative clicks on the AutoCAD window with `screenshotId`, and `type_text` to the AutoCAD window only after the command line holds focus (click the command strip once).
6. **Sky should NOT be reused by the desk's own scripts** (it is a bundled component of the Codex app; calling its helper outside Codex is unsupported). The deterministic runner uses plain Windows APIs instead: .NET UI Automation (System.Windows.Automation, with the Add-Type fix) and SendInput/SetCursorPos, which is what Sky does underneath, and what the Opus spec (TESTING_REBUILD_SPEC_2026-10-22.md) already plans. Driver v3 phase 1 is being built that way now.
7. **AutoCAD testing practice (web).** Forum and NuGet sources agree: code that touches the AutoCAD API can only be integration-tested inside AutoCAD (NUnit runners that load into acad: CADtest, JPP.AutocadNUnitTester.IntegratedRunner) or headless with `accoreconsole` plus a script that NETLOADs the add-in and runs a test-only command; core console cannot do interactive picks or windows. This matches our split: logic through scripts and test commands (deterministic, fast), picks and WPF windows through the pointer/UIA runner. Keep logic that does not touch AutoCAD in plain unit tests (CE already does: 19,000 Civil and 850 Manager tests).
8. **Codex rollouts.** `codex doctor`: 718 active rollout files, 28.57 GB; 2 thread-state issues (rollout files missing from the state DB; duplicate entries). A single run's file is 175 MB (embedded screenshots). `--ephemeral` skips saving but also removes the evidence we used today to find the fault; better to keep the last 7 days only.
9. **Other doctor notes.** Defender exclusions not verified; the worktree is not on a Dev Drive; an MCP server has missing env vars (optional); CLI 0.159.2 vs 0.163.0 available; desktop build 26.1016.8120.0 available; sandbox is unrestricted by design (`danger-full-access`).
10. **Windows notes (OpenAI docs).** Computer Use on Windows launched with the Codex app in late May 2026, runs in the foreground on the active desktop, and is not documented for locked or display-off sessions; the UK/EEA availability note in press coverage does not apply to a working install. The Windows sandbox (`mxc` / `elevated` / `unelevated`) is for shell commands; our runs bypass it.

## What this changes (the plan)

1. **Deterministic first.** Driver v3 and the case-file runner (Opus spec, phase 1 building now) do the repeatable work: exact pointer actions, window reading, clean lifecycle, assertions from logs and the drawing database. Target: the pack runs after every install and nightly with no AI at run time.
2. **Codex second, narrower.** (a) Window looks, using the accessibility text plus a screenshot, in 3 to 5 look briefs. (b) Review and authoring of test cases. (c) Failure triage on pack results. All Codex AutoCAD runs go through the attach probe and the conveyor; effort medium; results as `--output-schema` JSON plus the short report.
3. **Housekeeping.** Rollout clean-up (Tim's yes), Codex update after the weekend, Defender exclusions (Tim).
4. **Acceptance rule** (from the spec, for Tim): a logic result passes when the runner passes it in two separate AutoCAD sessions on the same build; a window/wording/appearance result needs a runner PASS plus a Codex look at the runner's capture.
