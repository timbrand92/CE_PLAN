# DIAG BUG-1279: Structural net48 geometry failures (5 Nov 2026, base 8de95c34)

1. **Verdict: ENVIRONMENT, not a product fault** (for the geometry tests). The net48 test run binds the AutoCAD 2024 "refs" DLLs at C:\Autodesk\CERef\AutoCAD2024-24.3.0\refs. Those are compile-only, IL-only stubs (PE flag ILOnly, no native code, no AutoCAD 2024 install on this PC). Any test that really calls Point3d, Vector3d or Matrix3d dies in about 1 ms.
2. **Group message (14 of 14 geometry failures identical):** `System.InvalidProgramException : Common Language Runtime detected an invalid program.` at Autodesk.AutoCAD.Geometry.Matrix3d.Displacement / Matrix3d.get_Identity / Point3d.get_X / Point3d.DistanceTo / Vector3d.get_XAxis / Vector3d.get_ZAxis. Three further tests Skip (not fail) with "acdbmgd.dll could not be loaded from C:\Program Files\Autodesk\AutoCAD 2027 ... incorrect format" (net48 cannot load the 2027 net10-only wrapper).
3. **The 12 names:** PickInAMovedUcs_IsCarriedToWorld; PickInARotatedUcs_FollowsTheRotation; WorldUcs_ChangesNothing; AnOverLongBrace_IsDrawnAtTheLengthPicked_NotCutToTheLimit; AUnchangedBrace_HasTheSameLengthEndPointAndRotationAsBefore (2 cases); ProductionPlannerAndMatrix_ExecuteEveryApprovedDetailedFamily; ProductionSectionMatrix_MapsPlannerAnchorToExactPickedPoint (4 cases: Degrees0/90/180/270). My filter also caught 3 more with the same InvalidProgram message: ZcOutline_IsACleanZ_ItNeverCrossesItself, ZcOutline_WebIsOneThicknessThick_AndTheFlangesPointOppositeWays, ZcProductionVertexBuilder_MatchesSharedTranslatedEnvelope (14 failures in total).
4. **The hang: it is a Sbeam compiled-route test, not a geometry test, and it is a HANG not a crash.** CompiledProductionRoute_BindsRealEntry... fails in 3 s with "R4 exact audited target assembly reference mismatch: acdbmgd" plus six R4 flow mismatches (the audit wants the exact audited AutoCAD reference, net48 binds 2024). The next stage then spins: CompiledProductionRoute_R10EveryUnsignedOpcodeHonoursAllInt64Boundaries("Bne_Un") ran 100 s with no result (blame hang timeout killed it; no stack overflow, no access violation, no exit code, host busy on CPU). Before that, 63 compiled-route cases passed in about 4 min (they are 2 to 3 s each, so the whole family is slow even when healthy). The earlier "crash" message is the harness aborting after my 10-minute cap / the 100 s inactivity kill.
5. **Own mistakes:** (a) my first compiled-route run used a wide name filter (about 130 cases) and hit the 10-minute cap before the hang test was found; a second run with a hang timeout found it. (b) I passed a Windows path to --results-directory from bash and it was mangled into a stray folder inside the worktree; removed with the worktree. (c) I did NOT run net10 (time budget, and the Structural native module / Visual Studio 2026 fault could block the build), so "same tests pass on net10" is untested. (d) I could not tell whether the R10 hang is product or reference-driven: it follows the R4 reference mismatch, so it may be the analyser looping because the net48 reference is not the audited one; unproven.
6. **Not mine:** testhost PID 95940 (started 13:45 today, about 1000 s CPU and climbing, no one told me it is theirs) is still running as I finish. It looks like exactly this hang in another session. I left it alone.

The 12 tests above do not call Ensure() (or call it after touching the types), so they run into the stubs and fail instead of skipping.

7. **Suggested direction for CE 00 (nothing done):** (a) geometry tests that need real AutoCAD types should Assert.Ignore when the loaded AcDbMgd is the IL-only stub, or run only on net10 with the 2027 install; (b) put a per-test timeout ([Timeout]) on the R10/R11 opcode tests so one spinning case cannot hold a whole-suite run for an hour; (c) decide whether the compiled-route proof is meant to run on net48 at all, since it audits an exact acdbmgd reference identity.
