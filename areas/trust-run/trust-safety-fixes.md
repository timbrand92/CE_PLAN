- 2026-11-15 07:50 READ-ONLY NOTE (no code): CDRUNSOLVE Apply and one U. Read in the batch 7/8 stack (wtB14g: RunSolveCommand.cs, ProposalApplyService.Apply, LinkService.ApplyPropagationPlan, LinkService.Reactors.cs OnCommandEnded, ProjectDataService.ReloadAfterDrawingHistoryChange).
  1. **What should happen:** one U straight after "Applied 5 change(s)" takes back every level CDRUNSOLVE wrote, both the drawing's level texts and CE's record. One accepted command is one Undo.
  2. **What the code does:**
     - **The whole Apply runs inside the CDRUNSOLVE command,** so AutoCAD makes it one Undo step: the held record refresh (refreshHold.Accept), ProposalApplyService.Apply, ApplyPropagationPlan's pipe and level writes, and ApplyPitOnlyChanges' pit inverts.
     - **CE's record saves are debounced** (SaveProjectData), but CE writes a waiting save at the end of its own command (OnCommandEnded, FlushProjectDataIfTriggerCommand: "write it if one is waiting"), so it joins the same step.
     - **After U,** CE re-reads its record from the drawing (OnCommandEnded, the U branch, ReloadAfterDrawingHistoryChange, CE-owned drawings only), so its memory follows the drawing.
  3. **A run that changes nothing still leaves its own Undo step.** CDRUNSOLVE is CommandFlags.Modal with no NoUndoMarker, and AutoCAD gives every such command its own step even when nothing in the drawing changed. Its record writes are held and put back in memory (HoldRecordWritesUntilAccepted / Dispose).
  4. **So in Codex's first test** (Apply, then another CDRUNSOLVE run, then U), the one U undid the second, empty run and nothing visible changed. A second U would have taken the Apply back. That is AutoCAD's normal one-step-per-command behaviour, not a CE fault, unless the clean re-run (U straight after Apply) also fails.
  5. **Where a real gap could be, if the clean re-run fails:**
     - **(a)** OnCommandEnded returns before FlushProjectDataIfTriggerCommand for CDRUNSOLVE: drawing not CE-owned, IsApplyingLinks set, or an exception. The record save would then wait for the NEXT command's end and sit in that command's Undo step. One U on CDRUNSOLVE would take back the drawing texts but not the record, and the re-read after U would then bring back the drawing's older record copy, so memory and texts could disagree.
     - **(b)** ApplyPropagationPlan or a level-text writer commits through a path that ends outside the command (Idle or a deferred attachment queue). It would land in a later step.
     - **(c)** ReloadAfterDrawingHistoryChange is skipped (IsCeOwned not true), so CE's memory keeps the new levels after U, and the next save would write them back.
  6. **How to tell them apart in the re-run:** after the single U, read CE's record in the drawing (CDCHECKCURRENT or the trust reader) and the level texts. Texts back but record new points to (a) or (c); texts not back points to (b), or to a run in between.
  7. **A possible change (not made; Tim's call):** a run that ends in "nothing to apply" or "Cancelled" could undo its own empty step, so U goes back to the Apply. This needs care, because AutoCAD's U is per command by design.
