# R-011. Grip shapes: can CE things use AutoCAD's own grip shapes (the arrows and triangles of dynamic blocks)?

Written Wed 18 Nov 2026, Melbourne afternoon, by the trials chat, for Tim's ruling D-244 ("EXTRA GRIPS OPTION BUT CAN YOU NOT DO SOME HARD PROPER RESEARCH AND TESTING TO SEE IF WE CAN AT LEAST USE AUTOCADS DIFFERENT CRIP TYPES LIKE IS IN DYNAMIC BLOCKS?"). Part 1 is research from sources read on this PC. Part 2 is the AutoCAD testing and is **NOT TESTED until each line below says otherwise**. Nothing here has been run in AutoCAD yet. No web addresses are in this file; sources are named by title or file path.

## The short answer

1. **Our own grip drawing its own shape (circle, diamond, triangle, flip double-arrow, stretch arrow, lookup triangle with bar) on an ordinary polyline, text or block: YES, it paints on AutoCAD 2027 (tested 18 Nov, pictures `evidence\r011\d_all_variants.png` and `h_all_shapes.png`).** These are shapes we draw, in our colour, that LOOK like the dynamic-block grips; they are not AutoCAD's own glyphs, because the 2027 .NET grip class has no shape setting and the ObjectARX 2027 reference has no class for dynamic-block parameters or their grips. The 4 Sep finding "AutoCAD paints nothing" is NOT true in general: the September cause is still unknown (see section 1 item 8). A custom grip that draws nothing is invisible: AutoCAD does not add its own square.
2. **Getting those shapes on CE things with no code of ours: yes in principle, by making the thing a small dynamic block.** AutoCAD then draws the grips from the block's own parameters, and a person with no plug-in gets them too. Cost: someone must author each block once in the Block Editor (there is no programming call to create a parameter or its grip), and a few behaviours are not yet checked (text, explode, speed). The office's pit block (PIT BLOCK 3) already works this way: a triangle for the kind and arrows for the size.
3. **What our own grip can do reliably:** sit in a chosen place, show words on hover, show one hover menu, and run an action when clicked. The 17 Nov crash was most likely our grip answering "Failure" to its own click; not proven, one-change-at-a-time test below.
4. **Recommendation (provisional until Part 2 pictures exist):** things that need a flip or a size drag and are blocks anyway get the block's own shape; things that are plain polylines and text get our grip in a chosen place with hover words. Section 4 gives the list a drafter can read.

## Part 1. Research

### 1. How dynamic-block grips get their shape, and what a plug-in can ask for

1. **What the 2027 .NET grip class offers (read from the decompiled wrapper).** `GripData` has these settings: IsPerViewport, GizmosEnabled, HotGripInvokesRightClick, ForcedPickOn, TriggerGrip, DrawAtDragImageGripPoint, ModeKeywordsDisabled, RubberBandLineDisabled, SkipWhenShared, AlternateBasePoint, GripPoint. Its overridable methods are OnHotGrip, OnHover, OnRightClick, WorldDraw, ViewportDraw, OnGripStatusChanged, GetTooltip, GetHoverDimensionData and GetHotGripDimensionData. **There is no shape, glyph type or icon setting.** The return enum has five values: Ok, Failure, NoRedrawGrip, GripHotToWarm, GetNewGripPoints. The draw-type enum has four: WarmGrip, HoverGrip, HotGrip, DragImageGrip. (Source: `C:\Tools\AcadDecomp\2027\acdbmgd\Autodesk.AutoCAD.DatabaseServices\GripData.cs`, `GripOverrule.cs`.)
2. **What the ObjectARX reference says about drawing a grip.** The grip data class "allows applications ... to draw their own grip glyph graphics". The viewport-draw callback is told: the drawing object, the entity, the draw type, a cursor position (only when the drag-image flag is set) and the grip size in pixels. The drawing object's colour starts as the current grip colour for that state. If the viewport callback returns false, the world-draw callback is called instead. **The area you can click is fixed around the grip's 3D point and is not decided by what we draw**, so the reference says to draw around or very close to the grip point. The grip flag list is: skip when shared, no rubber-band line, no mode keywords, draw at drag-image point, trigger grip, turn on forced pick, map hot grip to right-click menu, gizmos enabled, per-viewport, edit tip (internal), disabled, new-style right-click, synergy prompt. (Source: `C:\Tools\ArxDocs\arxref`, pages for the grip data class and `AcDbGripOperations__GripFlags`, `__DrawType`, `__ReturnValue`.)
3. **No documented request for a built-in shape.** I looked in the ObjectARX 2027 reference on this PC for any class for dynamic-block parameters, actions or grips (block flip parameter, block grip, block visibility parameter and similar names): **none exist there.** The only dynamic-block classes are the reference, its property and its block-record helper (read or set a parameter's value, list allowed values, say whether it applies in the current visibility state, convert to a static block). The decompiled 2027 .NET wrappers match: only `DynamicBlockReferenceProperty`, its collection and the dynamic members on `BlockReference` and `BlockTableRecord`. So the glyphs are drawn by AutoCAD's own block-editor code from a parameter's type, and a plug-in cannot reach them. **"Not documented" is not "impossible":** AutoCAD may draw them through an internal path I cannot see.
4. **Which parameter gives which grip (Autodesk's own help pages, read 18 Nov, AutoCAD LT 2027 versions; the full-AutoCAD pages were not read).** Point, Polar and XY parameters give a standard grip that moves in any direction. Linear moves back and forth along an axis. Rotation moves around an axis. Flip switches to a mirror image. Alignment moves in any direction and aligns the block with an object it is moved over, and always shows exactly one grip. Lookup and Visibility give a grip that opens a drop-down list. A parameter with no action shows no grip. "Number of Grips" can be set on every parameter except alignment. A visibility or lookup table can be set to show only the lookup grip. **The shapes themselves (square, arrow, triangle, round) are in pictures on those pages that I could not read, so the shape of each grip is from memory and UNVERIFIED until Part 2 test (a) gives a picture.**
5. **What the September attempts did (the repository's own note, `docs/research/GRIP_GLYPHS_RESEARCH_2026-09-04.md`, read in full).** Build 30a279ac on AutoCAD 2027, managed route: a filled circle drawn from the viewport callback with forced pick off, the same with forced pick on, and the same from the world-draw callback returning true: **nothing painted where the grip was, not even AutoCAD's normal square**, while the callbacks were logged as called. An earlier build with open lines painted nothing either, and a native C++ route did the same. Those tests were on text and block grips (no-filter overrules), not on a polyline. The one thing that did work on 4 Sep was one grip with a hover menu through the multi-function grip interface, on MText.
6. **How the September attempts differ from the Autodesk 2022 class handout that says it works (read this session from the downloaded PDF).** The handout's grip: sets the settings in the constructor (forced pick off, gizmos off, drag-image off, per-viewport off, no mode keywords, no rubber band, trigger grip on), draws in the viewport callback with a fill-always circle at the grip's X and Y with Z = 0, colour 30, size = 3 x the grip size divided by pixels-per-unit taken from `GetNumPixelsInUnitSquare` at the grip point, and **returns true**. Its click returns Ok (and elsewhere GetNewGripPoints). It sits on polylines and block references with a custom filter. It says nothing about which AutoCAD versions it was tested on; it is a 2022 document. The September test T1 matched this on size and fill, so the differences left are: the object class (text and block, not polyline), the filter type, and 2027 itself.
7. **Why the September drawing painted nothing: still unknown, but the 18 Nov tests rule several things out.** A clean grip class with the handout's pattern paints on 2027 on a polyline, on MText and on a block reference, in either callback, with forced pick on or off, with the drag-image flag, with Z from the point, returning true or false (section Part 2 (d)). So AutoCAD 2027 does paint custom grip drawings and the guess "2027 discards custom glyphs" is wrong. What is left is something in how the September code ran: the old Civil overrules used no filter (`SetNoFilter`) on MText and block references, the September grips were four grips at one spot as a set, the drawing used pipe-along axes (the handout and my test use plain X and Y), and the September build ran next to the other CE overrules and the old plug-in's native grip file. **None of these is tested.** The cheapest next test is the old pattern in my test plugin one difference at a time.
8. **A custom grip that draws nothing is invisible** (baseline, `d_baseline.png`): AutoCAD does not substitute its normal square. Any draw callback that throws, or draws something off screen, leaves the grip unseen but still clickable.

### 2. The route that needs no code of ours: make the thing a small dynamic block

1. **How it works.** In the Block Editor (or the block-editor command line forms) a parameter is added to a block and an action is attached. AutoCAD then shows that parameter's grip on the inserted block with no plug-in, and a person without the plug-in gets it too. The plug-in can read and set the parameter values through the property calls above (setting a value that is not in the list "succeeds and nothing changes", R-009 item 73). **There is no programming call to create a parameter, an action or a grip**: the blocks must be authored by hand once (or by driving the block-editor commands, which is untested here), then shipped in the office block drawing like PIT BLOCK 3.
2. **Candidates, each with its parameter and the grip AutoCAD should give (shape from memory until Part 2 pictures).**
   1. **Pipe label as a block:** flip parameter and flip action (flip arrow) plus a point or linear parameter with a move or stretch action (slide along the pipe). The text would be an attribute, so a plain double-click or ATTEDIT edits it. Not proven: whether the text stays readable when flipped.
   2. **Flow arrow block:** flip parameter and action (flip arrow).
   3. **Pipe-end marker:** a point parameter gives a standard square. **Nothing is gained over our own grip here**, because a standard grip is the same shape.
   4. **Pit tag and cover level text:** tags are separate text that moves with the pit (D-181, D-185); making them blocks adds grips but changes how text is edited. Not recommended without a test.
   5. **Inlet symbols (WITH MASK set):** already dynamic blocks (D-229): they already carry AutoCAD's own grips.
   6. **The pit:** PIT BLOCK 3 has one visibility parameter (the triangle) and linear parameters with stretch actions (the arrows). R-009 read this from the file; test (b) takes the picture.
3. **What it does to Tim's rules.** It keeps "ordinary objects only, works with no plug-in" (a block is an ordinary object). Typed-over label text (D-182) is an attribute value, which a plain edit changes. Printing: blocks print as drawn; a flip changes only geometry. **Unverified, to test:** MATCHPROP, copy (a copy should keep the dynamic state), explode (my understanding is that an exploded dynamic block loses its parameters and becomes plain geometry with attributes turned to text; UNVERIFIED), and speed with 60 on a sheet. **Known cost, UNVERIFIED here:** every distinct dynamic state can add an anonymous block definition to the drawing, so 60 flipped labels may add up to a number of hidden definitions.
4. **The honest limit:** the dynamic-block route gives only the grips a block parameter gives. It cannot put a flip arrow on a polyline or on bare text.

### 3. What our own grip can do reliably on 2027

1. **Proven on 2027 (R-006 section B and the September note):** a grip in a chosen place beside AutoCAD's own (the old Civil and Structural plug-ins do this daily); words on hover through the tooltip method; one grip opening a hover menu through the multi-function grip interface on MText ("Slide / Offset / Flip", Tim, 4 Sep, screenshot on #24); a trigger grip that runs an action on click.
2. **Settings the working shipping grip uses (R-006 B2 item 7):** trigger grip on, forced pick on, right-click menu off, gizmos off, mode keywords disabled, rubber band disabled, drag-image off, per-viewport off. **Click returns GripHotToWarm** (the old code's comment: "Return the documented warm state instead of leaving AutoCAD in an unspecified failure state"). The ObjectARX reference lists Failure as "an error has occurred and the grip operation has failed". Keep a strong reference to every grip until the grips are finished, because AutoCAD holds the grip after our method returns.
3. **The multi-function (hover menu) interface, read from the reference and the handout:** each mode has an id, a display string, a tooltip, a command string, a cursor and an action type (DragOn, Immediate, Command). The handout marks a menu grip as Secondary; **the reference says a Secondary grip shows only when GRIPS is 2** (Primary always shows when GRIPS is not 0). So to make a menu grip always visible it must be Primary: UNVERIFIED, test. The menu shows only when GRIPMULTIFUNCTIONAL is 2 or 3 (R-006). Attaching our own interface to a class replaces what AutoCAD has for that class, so on a polyline it could remove the native "Add vertex / Convert to arc" menu: only attach it to classes with no native menu (MText) or test first (test (e)).
4. **The 17 Nov crash diagnosis (R-006 B2 item 18, restated; not proven).** My trial grip differed from the old working grip in four ways: its click returned Failure; it set the right-click-menu flag with a managed menu; it kept no reference; and it did not set trigger or forced pick. The log showed the click method ran and AutoCAD closed straight after. Single changes to test, in this order, each in a fresh AutoCAD: run A old shipping settings returning GripHotToWarm, no menu; run B A but returning Failure (only to confirm the cause, and allowed to crash: if it does, record and carry on); run C A with the right-click flag and a menu; run D A with no reference kept.

### 4. Recommendation (provisional until the mouse tests (c) are done)

1. **Pit: AutoCAD's own grips from PIT BLOCK 3** (kind triangle with bar, size arrows). Seen on 18 Nov. No code of ours.
2. **Pipe label: the office already has seven pipe-label blocks (PT250 to PT600) with AutoCAD's own flip arrow, rotate dot and position square (seen).** If the new plug-in places those blocks, the label gets the real grips with nothing of ours. Whether the text stays readable under the flip, explode, and speed with 60 labels are NOT TESTED.
3. **Where a thing is a plain polyline, MText or non-dynamic block: our grip with a drawn shape** (flip double-arrow, stretch arrow, lookup triangle, dot) in a chosen place, hover words, and the click action returning GripHotToWarm. The shapes paint (seen); hover words, click and menu need test (c). They look like the dynamic-block shapes but are our drawings in our colour (orange in the test); they are not drawn by AutoCAD and AutoCAD does not know what they mean, so they need our plug-in to work.
4. **Pipe end: our square or dot grip with hover words such as "joined to P4".**
5. **Cover level text: our flip arrow** (the old plug-in already has a flip grip on MText).
6. **Inlets: the WITH MASK blocks' own grips** (position plus two flips, seen in the list).
7. **Not possible as far as proven:** AutoCAD's own glyphs on a polyline or bare text; a grip that is visible without a draw callback.
