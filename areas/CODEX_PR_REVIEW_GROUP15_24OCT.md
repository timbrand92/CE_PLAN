    **Why the locked case matters:** Autodesk documents that objects may be added to a locked layer but existing objects cannot be edited there. Its GetObject contract provides a separate forced-access parameter. The fix commits a new object, then attempts an ordinary write-open to erase it. This conclusion is derived from that contract and the code; the native exception and visible line have not been observed in this review. Sources: [Autodesk .NET layer locking](https://help.autodesk.com/cloudhelp/2016/ENU/AutoCAD-NET/files/GUID-505CCDA2-7060-4180-929C-CD065AD840D2.htm), [Transaction.GetObject](https://help.autodesk.com/cloudhelp/2026/ENU/OARX-ManagedRefGuide/files/OARX-ManagedRefGuide-Autodesk_AutoCAD_DatabaseServices_Transaction_GetObject_ObjectId_OpenMode__MarshalAsUnmanagedType_U1__bool__MarshalAsUnmanagedType_U1__bool.html).

    **Exact fix:** Collect the selected line or two proposed endpoints without changing the drawing. Resolve the required slab/system and output-layer protection before committing a driver. Alternatively, keep all driver changes in one uncommitted transaction that aborts on refusal. Do not unlock a layer or force access merely to compensate for an earlier committed write. Keep the existing REFEDIT/layout guard. Add a real native locked-destination case; the three present tests only inspect source text, and checking that cleanup contains no `IsLocked` cannot prove successful cleanup.
