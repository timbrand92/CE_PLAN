### 1. HIGH: "Command outcome" lines call successful Esc-finished commands "cancelled" (#1507, C-59)

1. **Where:** `Modules/Drainage/Services/CommandOutcomeLogService.cs` lines 62 to 80 (`Finish`) and 184 (`OnCommandCancelled`).
   The word is taken straight from AutoCAD's event: CommandEnded = "completed", CommandCancelled = "cancelled".
2. **What happens in AutoCAD:** PIT, CD, DP and other "keep placing until Esc" commands always end with Esc. AutoCAD reports
   that as a cancel, so the line says "cancelled" even when objects were placed. The reverse also happens: a CE refusal or a
   caught failure ("CE could not ...", "switched off ... Nothing was changed") ends normally and is logged "completed".
   CE's own CDINSPECTOR run at every AutoCAD start is logged like a drafter's command.
3. **Verified in the real log (22 Oct, Civil 3.0.69 and 3.0.70):**
   1. `14:39:34.451 Pit added: P8`, then `14:40:24.043 Command outcome: PIT cancelled 69339 ms`.
   2. Run 47: command line "Pit placed successfully." then `20:36:01.901 Command outcome: PIT cancelled 66877 ms`;
      "[CE] Pipe placed." then `20:37:01.891 Command outcome: CD cancelled 51957 ms`.
   3. `21:04:38.982 DP cancelled` and `21:12:49.990 DP cancelled` (downpipe block loaded just before; placement likely).
   4. CDCHECKIGNORE with the switch OFF (a refusal): `20:34:45.482 Command outcome: CDCHECKIGNORE completed 64 ms`.
   5. Whole day: 61 "completed", 17 "cancelled". LOG_OUTCOMES counted PIT as "worked" from other lines, so the two
      evidence sources already disagree.
4. **Why HIGH:** the desk ruled these lines are how the log "shows if a command worked" (1571), the 29 Oct watcher depends on
   them, and the robot's evidence for AI acceptance (RULES 13.3 amendment) reads the same log. Unit tests feed a fake "cancelled" event and pass;
   only real AutoCAD shows that Esc-to-finish is the normal ending. Same class as #1520.
5. **Structural has the same blind spot:** today's three CEMEMBER records in `runtime_20261022.jsonl` read
   `"status":"cancelled"`. CEMEMBER also finishes with Esc by design. Whether those three drew anything is unknown.
6. **Fix direction (for the builder, not Tim):** count drawing changes per command in memory (ObjectAppended / Modified /
   Erased events between CommandWillStart and the end; no transaction, no drawing access, REDO safe) and write
   "ended with Esc, drawing changed" versus "cancelled, nothing changed"; mark CE-started commands "(CE started it)".

### 2. MEDIUM: CDCHECKIGNORE saves the CE project record into the drawing before it checks its own switch (#1517, C-60)

1. **Where:** `Modules/Drainage/Commands/CheckIgnoreCommand.cs` line 35 calls `InitServicesFull(document)` BEFORE the switch
   check at line 37. `CeCommandBase.InitServicesFull` (line 43) calls `ProjectDataService.SyncWithDrawing`, which is
   `EnsureDrawingDataCurrent(db, force: true)` (`ProjectDataService.cs` lines 249 to 254): several whole-drawing passes,
   then a save of the project record when anything moved.
2. **What happens in AutoCAD:** typing CDCHECKIGNORE with the switch OFF prints "Ignoring a finding is switched off in CE
   Settings. Nothing was changed." But CE has just re-read the whole drawing and written its project record back. The
   same happens on every list read and every Esc with the switch ON. In a drawing whose record is out of date (a pit
   erased outside CE, a pipe copied) the record really changes, behind a "Nothing was changed" message.
3. **Verified in the real log, run 47 switch-OFF run:** `20:34:45.468 Project data saved to DWG successfully`, then
   `20:34:45.476 EnsureDrawingDataCurrent: 56.5 ms ran fully`, `20:34:45.482 Command outcome: CDCHECKIGNORE completed 64 ms`,
   then a second `20:34:45.484 Project data saved to DWG successfully` straight after the command ended. Every later
   CDCHECKIGNORE run shows the same pattern (for example 20:41:48 to 20:41:49).
4. **Claim corrected (RULES 6.2):** entry 1575 and the C-60 finalizer (section 1, item 2.5) say that with the switch OFF it
   "returns before reading anything". It does not: it syncs and saves first.
5. **It also explains run 47 finding C.2 in part:** every "read the list, then Esc" run is itself a command that wrote the
   record, so the next U undoes that read, not the earlier ignore. Even after a fix AutoCAD keeps one (empty) Undo step per
   command, so the wording "Type U to take it back" should say "straight away" (or the command should offer its own Undo).
6. **Cost on big drawings:** a forced full sync on every run; the robot needed about ten CDCHECKIGNORE runs for one
   ignore-check-unignore cycle.
7. **Fix direction:** read the switch first; list with `TryReadProjectWithoutChanging` and `InitServices` (no sync); run the
   sync only on the Ignore / Un-ignore path, just before `WriteIgnoredChecksInDrawing`.
8. **Deterministic test:**
   1. **Fixture:** fresh copy of DRV1_B1; Tim's CD_Settings.json has no `checks` group (so `allowIgnoreFinding` is absent, OFF).
   2. **Steps:** note the last line number of `CE_CVL_SUITE.log`; type `CDCHECKIGNORE`.
   3. **Assert:** the command line is exactly "[CE] Ignoring a finding is switched off in CE Settings. Nothing was
      changed."; the log lines after the noted line, up to one second after "Command outcome: CDCHECKIGNORE", contain no
      "Project data saved to DWG successfully" and no "EnsureDrawingDataCurrent: ... ran fully". Today: both appear, FAIL.
   4. **Second case:** switch ON (guard sets `checks.allowIgnoreFinding` true before launch), `CDCHECKIGNORE`, Enter, Esc
      at "Number of the finding to ignore:". Same assertion. Today: FAIL.
   5. **Source guard (no AutoCAD):** in `CheckIgnoreCommand.IgnoreFinding` the text `AllowIgnoreFinding` appears before any
      `InitServicesFull` or `SyncWithDrawing`.
