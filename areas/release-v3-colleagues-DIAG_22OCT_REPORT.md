## 2. Part 2(a): BUG-505, when the CHECK THE SCALE sentence prints

1. **How it decides** (`XcivilSourceUnitsCheck.Evaluate(guessedScale, insunits)`, called at `XcivilImportService.cs:328`, source units read by `ReadSourceInsunits`, `XcivilImportService.Pipeline.cs:111-126`). CE first GUESSES the scale from object sizes (1 = millimetres, 1000 = metres to millimetres), then compares with the source drawing's own INSUNITS (4 = millimetres, 6 = metres, 0 = Unitless, -1 = could not read).
2. **Prints a warning when:**
   - source says millimetres (4) but the guess is x1000;
   - source says metres (6) but the guess is x1;
   - guess is x1 and the source is any other recorded unit (feet, inches, centimetres and so on): "will read them as millimetres";
   - guess is x1000 and the source records NO units (0): "records no units, so the 1000 times scale is a guess";
   - guess is x1000 and the units could not be read (-1);
   - guess is x1000 and the source is some other unit.
3. **Silent when:** units and guess agree (4 with x1, 6 with x1000), AND when the guess is x1 and the source is unitless (0) or unreadable (-1). That last case is the one Codex hit: INSUNITS 0, scale 1, log line "check: scale agrees with the drawing's units". The log wording is slightly wrong for that case: it says "agrees" when the truth is "nothing to compare, assumed millimetres".
4. **What the drafter sees:** when it warns, the sentence is the FIRST line of the pre-flight text on the command line, before the pit and pipe summary, and it is also added to the import report warnings. In the X-Civil window route that line is printed behind the modal window and the window page itself does not show it (BUG-505 card, V3-04 note). It never blocks and never changes the scale.
5. **Does the card say unitless sources warn?** Partly. The HUNT2 card text says "where the units are not set it asks once" and "keep the guess only when UNITS are not set". The shipped fix and its REGRESSION_LOG entry deliberately narrowed that to "unitless AND guessed metres" (steps (c) of its own AutoCAD checklist test exactly that case). So code and the fix's own record agree with each other; they are narrower than the card's wish. Not a code defect. It does mean Codex's fixture (unitless, guessed mm) can never produce the warning, and V6-02 stays BLOCKED for the right reason: it needs a source with INSUNITS 4 or 6 that disagrees with the guess, or a unitless source whose objects look metre-sized.
6. **What Tim should decide (one question):** should a unitless (INSUNITS 0) consultant drawing that CE reads as millimetres still get one soft line, "this drawing records no units; CE assumed millimetres"? **Recommendation: yes, as a one-line note only, not the "CHECK THE SCALE" alarm.** Reason: unitless is common in consultant drawings, and a metre job with no pit between 0.05 and 3 units wide and no pipe line 1 to 250 long would be read as millimetres and come in 1000 times too small with no word said. The cost is one extra line on many imports. If Tim says no, keep as is and only fix the log wording. Not changed; a Tim call (never turned into a decision, rule 3.4).
7. **Not read:** the LandXML route (`Helpers/LandXmlParser.cs`) was not re-read for this question.

## 3. Part 2(b): progress line, V7 item 8 (#1514)

1. **Minimum real run length is 1.0 second.** `SlowWorkProgressTicker.Tick` is called once per model-space object (`Services/CurrentDrawingCheckService.cs:263`), writes only when `elapsed >= ShowAfterSeconds(configured)`, and then at most once per second (`RepeatSeconds = 1.0`).
2. **The 0.01 is clamped, and clamped up to 1.0, not to the floor.** `SlowWorkProgressRule.ShowAfterSeconds` returns the default 1.0 for anything below `LowestShowAfterSeconds = 0.5` or above 30 (or NaN). Test `ASillyDelayFallsBackToOneSecond` pins this for 0, negative, NaN and 500. So Codex's `0.01` behaved as 1 second. (A figure like 0.2 also becomes 1.0, not 0.5. That may surprise; it is by design "R-27: never a block", and could be a small wording or rule change if Tim wants. Not changed.)
3. **Switch and key names match.** Settings section `checks`, keys `showProgressWhenSlow` (bool, default false) and `progressAfterSeconds` (number, default 1.0): `Modules/Drainage/Models/UserSettings.cs:164-165` and `:2764-2769`. Codex readback confirmed boolean and number in `CD_Settings.json`. The command reads them when it starts (`CheckCurrentDrawingCommand.cs:56` and `:71`), but CE loads the settings file at AutoCAD start (memory: settings guard read at launch), so if Codex wrote the keys after AutoCAD had started, the switch would still have read OFF. The V7 report does not say which order was used. Unknown.
4. **Where it prints:** the command line (`editor.WriteMessage`), as "CE: checking the drawing, N objects read so far". Not log-only.
5. **Two other things that also silence it:** `interactive` is false when `CMDACTIVE` says the command came from a script or LISP (`CheckCurrentDrawingCommand.cs:63`, `PlacementContinuationService.IsScriptOrLispRun`, bits 4 and 32), and false if the checked drawing is not the active one. V7 says the command was "issued alone, once" and does not say whether it was typed or sent from LISP; if it was sent from LISP, no line can ever print.
6. **Verdict: not a defect; a drawing too quick for the rule.** Cancel with Esc is not built either (the code says so).
7. **How a Codex look can force it:**
   1. Easiest: a drawing with many thousands of objects in model space (a whole-site copy). Needs the walk to take more than 1 second; set `progressAfterSeconds` to 0.5 (the lowest value that is kept) so it shows sooner.
   2. Type the command at the command line, not via LISP or a script.
   3. Write the two keys BEFORE starting AutoCAD (settings read at launch).
   4. There is no debug key or slow-down switch. If Tim wants one, a deliberate test-only delay would be new work (needs a card).
