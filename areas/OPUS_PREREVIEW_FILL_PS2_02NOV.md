### #1410: BUG-779, moving the drawn Pit Schedule writes no cell text into the records

1. **What changes for the drafter.** `ScheduleLinkService.TryHandleEditedCell` (PR head `ScheduleLinkService.cs:227-261`) now runs three checks on every cell AutoCAD reports as edited, except the pit-number cell, which already had its own rule. The checks only run when the switch is on.
   1. **Same figure as the record:** the cell's number equals the stored figure, so nothing is written (`ScheduleCellEditDecision.EqualsStoredFigure`, `ScheduleCellEditDecision.cs:41`). For levels "equal" means within 5 mm, because levels are drawn to two decimals. For sizes, "2/375" counts as equal to 375.
   2. **Same text CE would draw:** the cell still shows what CE would draw, including a window override, so nothing is written (`Decide`, `:25`).
   3. **A real typed change to an overridden figure:** the cell is put back to CE's text and one command-line line is shown (`BuildPutBackLine`).
   Anything else is written to the record as before. This matches the carpark ("A move changes no record. Typing into an overridden cell ... is refused with a message") and the fix the carpark names.
2. **Switch.** `linking.scheduleMoveKeepsRecords`, ON (`UserSettings.cs`, the PR's hunk at about line 470; read at `ScheduleLinkService.cs:422`, falling back to ON). OFF makes `Decide` return WriteRecord, and the EqualsStoredFigure check is behind the same switch, so OFF gives the old code path exactly. The 5 mm tolerance is not an engineering value. It is half of the last drawn digit, because `FormatLevel2Dp` always draws two decimals, so it does not belong in Settings (R-00 is fine).
3. **No hard blocks (R-27).** The put-back is a command-line line (`SayPitCellLine` writes to the log and `Editor.WriteMessage`). There is no window and no refusal of the command. Pass.
4. **Protection, Undo and REDO.** The only new drawing write is the put-back (`entity.UpgradeOpen()` + `SetEntityText`). It uses the same pattern, in the same function, as the existing copied-cell and external-cell put-backs. It runs in the end-of-command link pass (`LinkService.PipeAttachmentUpdates.cs:50`). The reactor does not queue edits while U, UNDO or REDO are running (`LinkService.Reactors.cs:65`, IsSuspended), so a put-back cannot fire after a U and throw REDO away. The REDO-safe hooks baseline change is exactly the second UpgradeOpen in `TryHandleEditedCell` ("(x2)", three lanes). That is honest and matches the code. A locked-layer cell cannot be MOVEd or typed into by the user, so it never reaches this code. No PROTECTED file is touched (`ScheduleLinkService.cs` is not on the protected list; `TryParseLevelNumber` went from private to internal, with no change in behaviour).
5. **Merge.** See Group fact 5. Inside the group, no other PR changes `TryHandleEditedCell`.
6. **Tests.** `ScheduleCellEditDecisionTests` (11 tests plus 8 cases) cover the decision, the tolerance, the override names, the switch default, and two source guards (the handler calls the decision, and checks the stored figure first). The REGRESSION_LOG says plainly that they were "written with the change, not run red first", because the decision class did not exist before. No test drives `TryHandleEditedCell` itself, which needs AutoCAD.
7. **NOT proven, and the notes.**
   1. **Stale cell:** if a cell shows an old figure (record changed, cell not refreshed) and the figure is not an override, a MOVE still writes that old figure into the record. The same happens when CE cannot work out the cell text (`BuildCellText` returns null, for example a pipe side marked stale): `Decide` returns WriteRecord. This was already the behaviour and is now much narrower, but the carpark's "a move changes no record" is not true in every case.
   2. **Small typed changes:** a typed change of 5 mm or less to a level is silently left alone, and the next refresh redraws the old figure.
   3. **Override equal to the record:** if a cover is overridden to 21.50 (record 21.00) and the drafter types 21.00 into the cell, the "equals record" check leaves it alone silently. The cell shows 21.00 until the next refresh puts 21.50 back.
   4. **Noise risk:** if an override's drawn text ever differs from `BuildCellText`'s raw override text (spacing or formatting), a plain MOVE would trigger the put-back line. I read both paths and expect them to match, but this has not been seen.
   **Robot scenario (CE 02), copy drawing only:**
   1. A pit P3, cover 21.00, inlet pipe 300. PITSCHEDULE: override P3's cover to 21.50 and the inlet to 375. Place the table and close the window.
   2. MOVE the whole table 5 m. Expect: P3's cover is still 21.00 in Edit Pit, the pipe is still 300, and no "[CE] This Pit Schedule cell" line appears.
   3. STRETCH a corner, then grip-move. Same expectation.
   4. Set a cover to 21.125 in Edit Pit, refresh the table, MOVE it. Expect 21.125 kept, not 21.13.
   5. Double-click the overridden cover cell and type 21.60. Expect the cell to go back to 21.50 and one command-line line.
   6. Type 21.40 into a non-overridden invert cell. Expect the pipe invert to become 21.40 (a real edit still works).
   7. U once. Expect the edit undone. Then REDO. Expect REDO is still offered and works.
   8. Settings OFF, repeat step 2. Expect the old behaviour: the cover becomes 21.50.
   **Codex look:** one screenshot after step 5 showing the command line.
8. **Verdict: KEEP-WITH-NOTE.** Nothing needs changing before it ships, because it already has. Train class FULL: it runs after every edit of a drawn schedule cell, for every colleague. It already rode the C-trains from 3.0.70, so there is nothing to re-run except the robot scenario above.

### #1422: BUG-786, a new inlet stays with its pit in the Pit Schedule window

1. **What changes for the drafter.** Only `PitScheduleViewModel.ApplyPersistedSortOrder` (`PitScheduleViewModel.Data.cs:859`, the sort at about lines 918-928) changes. It now calls the new `PitScheduleRowOrder.Arrange` (`PitScheduleRowOrder.cs:21`). Rows are grouped by pit handle plus schedule set. A pit takes the earliest saved place of any of its rows. Inside the pit the saved order is kept only when every row has a saved place and the saved first row is still the row the build puts first (the fix round). Otherwise the pit's rows go back to build order, lowest inlet first. Manual rows stand alone and keep their place. Brand-new pits go to the end, as before. This is the carpark's "apply saved order at pit-group level", and it gives "a pit's rows stay together, in invert order".
2. **Switch.** `linking.scheduleRowOrderByPit`, ON, read at the call site with a fallback to ON. OFF runs the exact old `OrderBy(saved).ThenBy(index)` inside `Arrange` (`PitScheduleRowOrder.cs:24-27`), so it is identical to before. No engineering value is added.
3. **No hard blocks.** None. The change is only to row order in the window.
4. **Protection, Undo and REDO.** Window-only ordering. No drawing write and no protected file. The saved sort map is written by the existing save path, which is unchanged.
5. **Merge, and which function each sibling changes in `PitScheduleViewModel.Data.cs`:**
   1. **#1422 (this PR):** `ApplyPersistedSortOrder` only.
   2. **#1431 (job 613):** `LoadFromProjectData`, `LoadFromSelectedXrefs`, `OnRowPropertyChanged`, `UpdateWarning`, `ComputeDiameterWarning`.
   3. **#1415 (job 615):** `LoadFromProjectData`, `AppendExternalSourceRows`.
   No two of these touch the same function as #1422, and `git merge-tree` merges `Data.cs` cleanly for #1422 with each of them. #1431 and #1415 share `LoadFromProjectData` with each other (not with #1422). That pair is for jobs 613 and 615. Both are already on the train as well.
6. **Tests.** `PitScheduleRowOrderTests` (9) run the pure rule. `ANewInletToP5_StaysWithP5` and `SwitchOff_TheNewRowGoesToTheEndAsBefore` show the difference between the old and new rule on the same rows, which is a fair before and after. There is a source guard that `ApplyPersistedSortOrder` calls `Arrange`, and the switch default is pinned. The rule cannot be exercised through the real window without AutoCAD.
7. **NOT proven.**
   1. **The BUG-008 cut-off still applies first** (`Data.cs` about 873-893): if fewer than 90 % of rows have a saved place, the whole saved order is thrown away. With one new inlet in a 10-row table that is 10 of 11 (91 %), so it passes. With 2 new rows in a 10-row table (83 %), the whole saved order is dropped and the build order is used. That is BUG-1023-class behaviour (carpark line 13945), not a fault of this PR.
   2. **External (Xref) rows:** they are grouped by the source pit's own handle plus schedule set, not by drawing (`SourcePitHandle = pit.EntityHandle`, `Data.cs` about 797). Two Xref drawings whose pits share a handle and a schedule set could be pulled together. This is unlikely, it only affects row order, and it is the same family as the #1431 Xref note in PS1.
   3. **Drag order inside a pit is dropped** once a new row joins that pit. This is intended and documented in `PitScheduleRowOrder.cs:11`.
   **Robot scenario:** 10-pit drawing. PITSCHEDULE, drag P10 to the top, Save, close. Add a second inlet to P5 (higher than the first), reopen PITSCHEDULE. Expect P10 at the top and P5's two rows together in fifth and sixth place, with P5's number on the first of them. Repeat with the new inlet the lowest: expect the new row first within P5, carrying P5's number and cover. Settings OFF: expect the new row at the bottom (old behaviour).
8. **Verdict: KEEP.** Train class Civil area + smoke.

### #1420: BUG-798, a continuation sheet repeats the pit columns

1. **What changes for the drafter.** When a pit's rows cross a sheet break, the row heading the new sheet now shows the pit columns (1 number, 2 size, 6 outlet size, 7 outlet level, 8 cover, 10 lid and remarks). They are read from the pit's first row through `PitScheduleContinuationLayout.HeadingRowFor` (`PitScheduleContinuationLayout.cs:124`) and the new `headingRow` argument of `FormatColumnText` (`PitScheduleViewModel.Schedule.cs:1712`). FROM, inlet size, inlet level and depth stay the row's own. The repeated cells are linked to the pit's first row (`LinkRowFor`, `Schedule.cs:1640`, from the fix round), so they refresh and are edit-checked like the original cells. This is used at both drawing routes: first placement (`Schedule.cs` about 1278 and 1308) and the in-place update (`BuildDesiredScheduleCells` about 1387 and the patch at about 1577). It matches the carpark ("P12 and its pit columns repeated on the new sheet"). It reaches that by reading the first row when formatting, not by the carpark's suggested "store pit fields on every row". Same result, smaller change.
2. **Switch.** `linking.scheduleContinuationRepeatsPitColumns`, ON (`PitScheduleContinuationLayout.cs:147`, falling back to ON). When OFF, `HeadingRowFor` returns null, so `FormatColumnText` uses the row itself (blank pit cells, skipped as before) and `LinkRowFor` returns the row itself. Old behaviour exactly. Column numbers are layout constants, not engineering values.
3. **No hard blocks.** None.
4. **Protection, Undo and REDO.** It adds cells within the existing schedule placement and patch transactions. No new write route and no protected file. Cells that used to be skipped as blank now exist, so a drawn table updated in place gains a few new MText cells at sheet breaks. The existing patch code adds them in its normal way.
5. **Merge.** See Group fact 5. No sibling in this group or in 613/615 changes `FormatColumnText`, `LinkRowFor` or `HeadingRowFor`.
6. **Tests.** `PitScheduleContinuationPitColumnsTests` (7 tests plus 10 cases) cover `HeadingRowFor` (sheet head, mid-sheet, own-pit start, three rows, switch off), the pit-column list and the default. Weak guard: `TheRepeatedPitCellsAreRegisteredWithTheHeadingRowsLinks_AtBothCallSites` counts "LinkRowFor(rows" at least once. Since "LinkRowFor(rowsToPlace" itself matches, it passes with only the placement route wired. Its message claims both. I read the code, and the patch route at about line 1580 does call `LinkRowFor(rows, ...)`, so the code is right but the guard would not catch a regression there. There is no test of `FormatColumnText` output, because it is private and drawn-only.
7. **NOT proven.**
   1. Nobody has seen sheet 2 drawn.
   2. With #1410 ON, a MOVE of a two-sheet table should leave the repeated cells alone, because their text equals CE's text for P12's first row. Not seen.
   3. Excel or PDF exports of the schedule do not go through this `FormatColumnText` (it is private to the drawn table), so an export may still show blank pit cells on a continuation. Not checked; outside this bug's wording.
   **Robot scenario:** set rows per sheet to 20 (or use a drawing that gives 21+ rows) with P12's two rows at rows 20 and 21. Place the table. Expect sheet 2's first row to read P12, its size, outlet size and level, cover and lid, with FROM, inlet and depth from P12's second row. Change P12's cover in Edit Pit. Expect both the sheet 1 and sheet 2 cover cells to update. MOVE the table. Expect no record change and no put-back line. Settings OFF and re-place: expect sheet 2's pit cells blank (old behaviour).
8. **Verdict: KEEP-WITH-NOTE** (the note is the weak source guard; a follow-up test could count `LinkRowFor(rows,` and `LinkRowFor(rowsToPlace,` separately). Train class Civil area + smoke.
