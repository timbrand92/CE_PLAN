# The loops that carry the plan (draft 1, for Tim to approve)

**Why this file exists.** Tim, 18 Nov 2026: "the plan needs to create the best possible loops for the overall plan." A loop is work that keeps going round by itself until it is right, and only stops for Tim when it truly needs him. Written by the planning chat. **Status: draft.** Loops 1, 4, 5 and 6 are running now. Loops 2 and 3 need Tim's yes (section 3).

## 1. The six loops

1. **Tool loop (one tool at a time, D-091).** Mock-up Tim approved → Sonnet builds → a separate Opus reviewer → real clicks by an independent tester → faults back to the builder → round again until the tester finds nothing → on Tim's list to try. Runs in the build chat. Stops for Tim: never, until the tool is ready for him.
2. **AutoCAD night loop.** Every night inside Tim's hours rule (5:30 pm to 8:30 am, all weekend), on test copies only: start AutoCAD the normal way, run tonight's tool through its everyday job by robot, read back what was drawn, close AutoCAD, send faults to the tool loop. One command per step, read back after each. Stops for Tim: a licence or sign-in window, or anything that is his own AutoCAD.
3. **Real-job loop.** Each tool that passes loop 2 is run through a finished job copied under a coded name (allowed 15 Nov), and the sheet compared with what the office issued. Differences go back to the tool loop.
4. **Decision loop.** Anything that is Tim's call is taken at the recommended answer, marked DRAFT, and collected. Once a day he gets them as one batch of clickable questions, at most 12, each with a real-job example. His answers go into the lists the same day.
5. **Director loop.** `DIRECTOR_SUMMARY.md` is refreshed after every piece of work, so "how are things going" is always one page: planned, built, how close, problems, waiting on Tim, next step.
6. **Keep-moving loop.** A timer wakes the planning chat about every 30 minutes. It reads `LOOP_QUEUE.md`, moves the first thing that can move, nudges a side chat that has stalled, and checks nothing is stuck, the disk has room and usage is on pace. When a queue empties it refills it from the plan's order of work, never from outside the plan.

## 2. The rules every loop keeps

1. Built, tested, installed, accepted stay four separate facts. A loop never calls its own work accepted.
2. Nothing new while a ribbon tool is broken (D-090): a fault always goes ahead of new work.
3. The builder never tests its own work. The tester never fixes.
4. Rule 1.9 in full. No profiles, licence, sign-in, registry or saved settings.
5. Nothing is installed on Tim's PC by a loop. Installing is always Tim's yes.
6. No client names, job addresses or job numbers.
7. A loop that fails the same way twice stops and says why, rather than trying a third time.

## 3. What the loops need from Tim to run without him

1. **Yes to start the AutoCAD part** (the foundation, then Pit, then Pipe). Without it loop 1 runs dry after the seven bench windows.
2. **A standing yes for the night loop**: AutoCAD may be started on test copies every night inside his hours, without asking each day.
3. **A standing yes to close a TEST AutoCAD the robot itself started** (normal close, then force) when it jams or crashes. Without this, one jam stops the whole night, as on 17 Nov. It would be written into rule 1.9 as a named exception: only an AutoCAD the robot started that night, only on a test copy, never one of Tim's.
4. **The PC left on**, and the Claude app open.

## 4. What no loop can do

1. Tell whether a sheet looks right to an engineer. That is Tim, on one real job.
2. Decide engineering figures. They are asked, never guessed.
3. Replace Tim's acceptance (or a robot pass when he is busy, D-089).
