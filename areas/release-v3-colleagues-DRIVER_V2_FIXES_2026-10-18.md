## 1. HIGH 1: click-canvas clicked whatever window floated over the drawing area. FIXED, proven live.

1. **Fix:** the click now needs the window under the pointer to BE the drawing area (the window found at calibration) or a child of it. The check is made twice, the second time with the pointer already on the point. A floating CE window, a palette or another program over the point is refused. The drawing area must also still be the same window as at calibration (its handle is compared, not only its position).
2. **Related fix (folded in from LOW):** the click decision no longer assumes a command is waiting. It reads the same command-line evidence as `esc-prompt`: lines printed since the driver's last send, and the last finished line must be about a point, a corner or objects. First attempt failed in AutoCAD: AutoCAD writes the waiting prompt to its log only when the line is finished, so a waiting LINE shows as "Specify first point: 123,456", not as the waiting prompt. The rule was relaxed to that, and the guide says it is weaker than seeing the waiting prompt.
3. **Refusals proven offline:** a floating window of the same process over the point (`other_window_under_point`), a frame of another process, a point outside the drawing area, no drawing-area window recorded, a "canvas" that is not inside the frame, ClickAt itself refusing before any mouse move, plus the decision cases: busy but no command-line lines since the send (the Pit review hang state), busy with a last line that is not a point prompt, a log ending on an idle Command: line.
4. **Refusals proven live (AutoCAD 2027):** with the Edit Pit window open over the middle of the drawing area, the click was refused (`target_check` `other_window_under_point`, reasons listed). With a topmost window of another program over the point while a LINE really waited for a point, the click was refused (`other_process_under_point`). Right after, the normal click worked: wanted 72801.8,-61633.3, got 72845.1,-61603.9 (one pixel).
5. **A mistake of mine on the way:** my first foreign-window test failed because the test window sat BEHIND AutoCAD (topmost was not honoured), so a click really went through once, on the test copy, with a LINE waiting. The test now forces the window to the top before it asserts. The click was on a throwaway line that was undone.

## 2. HIGH 2: the settings guard. All 7 parts FIXED.

1. **2.1 Tim's own AutoCAD:** `settings-temp set`, `arm` and `snapshot` refuse while any acad.exe runs that the driver did not launch, or while more than one runs. **Live:** AutoCAD started through Explorer (not the driver) on a test copy; set, arm and snapshot were all refused ("did not launch"), the scratch file was unchanged, no manifest was created. In the same stage `save-copy`, `click-canvas` and `esc-prompt` were refused for the same reason. The real settings files were not touched; their hashes were read before and after.
2. **2.2 A restore while AutoCAD runs threw the safety net away:** now a restore while AutoCAD runs puts the file back but KEEPS the backup and the manifest (marked restored_while_running). `quit` restores again after AutoCAD has ended, re-hashes every file, restores again if CE rewrote it on closing (the changed file is copied aside first), and only then deletes the backups. **Live:** set, restore mid-session (kept 1), set again, quit: hash equal to the original, manifest and backup gone. Also proven offline with a rewritten-on-close file.
3. **2.3 No recovery if the session ends without quit:** the restore hook is now a `finally` (a call that ends unexpectedly runs it: proven with a child process whose call blows up; the file came back and the manifest went). The hard-timeout watchdog leaves an "abandoned" mark (proven: exit code 2, mark written when a manifest exists, no mark when none). The NEXT driver start restores first and says so, when the pass that made the backups is over (lock released, expired or taken over) or the mark is there (proven through the real driver both ways). `lock release` restores first when AutoCAD is not running and refuses (the lock stays) while AutoCAD runs or a restore fails (proven). `launch` refuses while a restore is unresolved (proven; AutoCAD was not started). Every result shows the guard warning in plain words in the output lines, `status` included.
4. **2.4 The restore overwrote without looking:** the guard records the hash of what it wrote. A file that is neither the original nor that is somebody else's change: BOTH are kept, the changed file is copied next to the backup, nothing is overwritten, the manifest stays, a loud `!!!!` line is printed. `settings-restore -Force` restores anyway after the copy. Files that `arm` covers are the one exception (the Settings window is expected to change them): copied aside, then restored. Proven offline and through the real driver (someone else edits the scratch file after the set: restore fails loudly and keeps everything; `-Force` then restores).
5. **2.5 The restore could be capped away:** `quit`, `lock`, `status`, `help`, `settings-restore` and `settings-temp status` are never stopped by a verb cap or the total cap (a decision test, plus the real driver with the total cap set to 1: status and restore worked, a snapshot was refused by the cap).
6. **2.6 The manifest could be hidden:** it now lives in the driver's own folder whatever `ACAD_DRIVER_HOME` says, and v2 write verbs refuse while that variable is set. Every restore re-checks each entry (allowed file name and folder, no link on the path, backup inside the backup folder): a backup path outside the folder and a manifest entry naming a file outside the allowed folders were both refused.
7. **2.7 arm missed missing files:** every watch file now gets an entry, a missing one as existed = false, and the guard is armed only when all four have one. A file the Settings window creates is removed by the restore (proven).

## 3. MEDIUM findings: all FIXED

1. **3 The lock was not required:** `ui press`, `ui set`, `pick-first`, `dialog-path`, `save-copy`, `reopen-copy` (and `esc-prompt`, `click-canvas`, `settings-temp`) now refuse without the lock held by the caller. Proven through the real driver, one refusal per verb, with no lock held.
2. **4 The Settings gate depended on the title:** any window with "settings" in its title is gated (a "Pit Schedule settings" window is no longer let through by the first entry that matches), and a settings-titled window that is not on the list is refused. The 4 real settings files' SHA-256 are read at `lock acquire` and printed, and read again at `quit` or `lock release`, compared and printed; a change outside the guard is reported loudly. **Live result: the 4 real files had the same hashes at the start and the end (ACD64E79A33B, 622A246F7D3B, 24D8E5F7D87B, EFE307C4FC74).** A changed file was caught in the offline test.
3. **5 The hard timeout cut long verbs off:** `save-copy` and `reopen-copy` default to `-TimeoutSec 120` in the driver (proven: 120 / 120 / 20 given / 15 for other verbs), their hard timeout is 150 s (was 30), and each writes a start line to the audit log before it acts.
4. **6 The never list was weaker than the old deny list:** the never patterns now match anywhere in the name (`*Delete*`, `*Overwrite*`, `*Remove*` ...), and the old whole-word deny list also applies: always to `ui set`, and to `ui press` except the exact names a window lists as exceptions (Save pit and close, Save pipe and close, Continue placement in the New windows, Update in Pit Schedule, Save in Settings). Refused in tests: toggles or buttons named "Confirm delete", "Yes, overwrite", "Pit remove", "Delete all pits", "Overwrite existing", "Replace block", "Save as draft", and a plain "Save" in Edit Pit. An exception never excuses a hit on the control id. **Live:** Save pit and close, Cancel without saving, Refresh, Relink and recalculate, Choose DWG and Close all still worked.

## 4. LOW findings: all FIXED

1. **7 The "driver started it" record is weak:** the guide and the esc-prompt refusal text now say plainly that `v2_state.json` is a record, not proof; the real boundary is the AutoCAD the driver launched.
2. **8 Soft caps:** the counter belongs to the pass (the lock's start time), so renewing the session id no longer resets it (proven); v2 write verbs refuse while `ACAD_DRIVER_HOME` is set (proven). The guide says the caps are a discipline aid, not a wall.
3. **9 Not every refusal was audited:** one `call_end` line is written after every v2 call, refusals, cap refusals and lock refusals included (checked in the audit file); a failed audit write shows as `audit_write_error`.
4. **10 No 60-minute stop:** v2 write verbs refuse 60 minutes after the lock was taken; `quit`, `lock`, `status`, `shot`, `settings-restore` and `settings-temp status` still work. Proven through the real driver by ageing the lock 62 minutes.
5. **11 The report overstated the allow-list pin:** the guide now says which verbs never read the list (`esc-prompt`, `click-canvas`, `pick-first`, `shot`, `settings-restore`).
6. **12 save-copy accepted every old CLD copy:** only the copy this session launched, opened or created with SaveAs may be saved or reopened. Refused offline: an old CLD copy, and any copy when the session list is empty.
7. **13 The shot screen fallback:** the screen copy is taken only if the window is the top-level window at its four corners and centre; otherwise no screen copy (`screen_copy_refused`). The top-window lookup is tested offline; the refusal path itself was not provoked in AutoCAD (PrintWindow worked every time).
8. **14 dialog-path accepted fixtures and backups:** `DRV*` names, `_PRE_` and `.bak` files, the settings-guard backup folder and paths with a link are refused (tested).
9. **15 Path guard gaps:** a junction or symbolic link anywhere on a test path is refused (tested with a real junction), and a `*_VERIFY*` folder counts only on drive C:.
