# FOR TIM

1. **The fix is right and small:** when CDTAG renames a downpipe or other source that already has a tag, the point where pipes join it now stays where it was, instead of jumping back to the block's insertion point. Only the tag (and the label, if asked) changes. Pipes that met the old point still meet it.
2. **On drawings made with today's CE nothing changes at all:** today's CE always puts that point on the insertion point, and a MOVE or ROTATE carries it with the block, so the result is the same as before. The fix matters for sources tagged by an older CE that let you pick the point, and copies of those.
3. **The AutoCAD check it hands the robot cannot be done as written:** it says "nudge the connection point with the grip", but there is no grip for that point in the installed CE. The robot needs a test copy holding a source whose point is away from its insertion point (an older drawing, or one set up on a copy) and must read the stored point before and after.

**Verdict: GO** for the robot on copies, once the robot step is corrected (words only, no code).

# Findings (file and line at `38ac37ce` unless stated)

1. **The change, by reading: right.**
   1. `Commands/SourceTagCommand.cs:346-354`: on a retag, the stored point is read with `SourceTagService.TryGetConnectionPoint` (`Services/SourceTagService.cs:770`, read-only opens of the extension dictionary and record) and handed to the existing retag request in place of `blockRef.Position`. `Rules/SourceRetagConnectionRule.cs:10-11`: stored point if there is one, else the insertion point, as before.
   2. The point reaches the drawing through the same one route as before: `LinkService.PrepareSourceChangeInTransaction` (projection) then `SourceTagService.WriteSourceChange` (`Services/SourceTagService.SourceChangeApply.cs:35-36`, `SetConnectionPoint` from the request) and its read-back, which compares the written point with the request, not with the insertion point (`SourceChangeApply.cs:61-69`). The drawing-wide read-back (`LinkService.SourceChangeApply.cs:321-375`) never compares the point with the insertion point. So no read-back rejects the kept point (the trap PR 2085 fell into does not exist here).
   3. **It also stops a knock-on the bug only hints at:** the plan works out which pipe ends belong to the source from the PROJECTED point (`LinkService.SourceChanges.cs:421-430`, `ProjectedSource` replaces the stored point with the request's). Before, a retag projected the insertion point, so a pipe end that met a point picked away from it could be counted as no longer the source's and re-planned. Now the projection is the point the source already has, so the pipe ends resolve as they did.
   4. **A stale point is not possible:** the point is stored relative to the block (block-local through the block transform, `SourceTagService.cs:686-697`, or as an offset from the insertion point for old records, `SourceTagService.SourceChangeRead.cs:91-101`), so MOVE, ROTATE and SCALE carry it, and CE refreshes it after an outside move (`LinkService.SourceMoves.cs:375-381`). Keeping it can never leave the point behind where the block used to be.
   5. **Today's drawings unchanged:** every placing path in the installed code writes the point at `blockRef.Position` (`SourceBlockInsertCommands.cs:351`, `WaterTankCommand.Apply.cs:272`, `SourcePlacementService.cs:1075,1206,1360,1509`, `XcivilPitInsertionService.cs:651`; the landing path at `LinkService.SourceLanding.cs:660` requires the landing point to equal the placing point, line 615). For those, the stored point resolves to the insertion point (block-local zero), so the request is the same point as before.
2. **Only what the bug needs:** one read and one choice in the retag branch; no new prompt, word on screen, switch or Setting. The radius is still written as the standard 150 mm catch circle, as before (the bug is about the point only).
3. **One U:** unchanged. The read happens in the command's existing transaction before the plan; the write is the existing single source-change apply.
4. **Nothing protected bypassed:** the change only reads. The plan's own checks still run (model space only, writable source, the round-trip check of the point through the block transform, `LinkService.SourceChanges.cs:244-250`, locked-layer and Xref refusals unchanged).
5. **Plain words:** no drafter-facing text added. The REGRESSION_LOG entry is plain and does not overclaim (built and unit-tested only).
6. **Robot step wrong (the one item before the robot runs).** No grip for a source's connection point exists in the installed code (no grip overrule on sources: the only grip overrules are for pipes and pipe Mlines, `CompoundGripOverrule.cs`, `PipePlanGripOverrule`, `PipeAttachmentActionGripOverrule`; no command moves the point except the paths in 1.5, which put it on the insertion point). PR body item 6, REGRESSION_LOG item 4 and `PENDING_TESTS.md` row 29 all say "nudge its connection point with the grip". Replace with: (a) on a test copy holding a source whose stored point is away from its insertion point (one tagged by an older CE that asked for the point, a copy of one, or one set up on the copy by the evidence lane), read the stored point, CDTAG it to a new tag, read it again: unchanged, and the pipe end still owned by the source; (b) the everyday case: a source tagged by today's build, retagged: point still on the insertion point, nothing else changed. The bug entry's own step 1 has the same wording; worth correcting there too (carpark owner).
7. **Tests: fail without the change, but not through the real code path.** Two tests check the three-line rule; the third is a text search of `SourceTagCommand.cs` for the new call and the absence of the old line, so it fails on `cf059dcf`.
