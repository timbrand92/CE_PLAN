## #1975 IN FULL: THE TIDY AFTER EVERY PIT MOVE (the heavy one)

1. **What starts it, how often, on what:** the existing tidy `TidyTextClashesAfterNativeMove`. It runs at the END of the drafter's own edit command (MOVE, -MOVE, STRETCH, grip moves) through `LinkService.Reactors.cs` (the established route and the typed-straight-pipe route, and after an attachment-only move), from CE's own pit moves (`LinkService.PitMoves.cs`), Edit Pipe, CD's pipe creation, source placement, and Tidy labels' count and Apply. On a MOVE it runs once, over the CE pipes the move touched (the pipes of the moved pit), not the whole drawing. #1975 adds no new caller.
2. **Does it open a transaction, write an object, move a text?** The tidy already opens one normal transaction per run (`RedoSafeReviewedHooks.baseline.txt` line 665, reviewed). #1975 adds no transaction. It adds one more reason for a text to count as clashing: its true turned rectangle touches the strip of its OWN pipe (half the pipe's diameter each side; a twin detention pipe's full width). When that happens and a clear spot exists, the EXISTING writer moves that text (it rewrites the pipe's record and the text's place, inside the same transaction). So yes: **with #1975, a MOVE can now move a text that would not have moved before**, through the old writer only.
3. **How the rectangle is measured:** a copy of the text, turned back to run along X, is made outside the drawing, its extents read, and the copy disposed at once (`TryReadOrientedTextRect`). Only a text (DBText) or multiline text (MText) is measured; a flow-arrow block, a callout (MLeader) or anything else gets no rectangle and keeps the old answer. My class pins that the measuring routine has no write, no `tr.`, no append and is disposed.
4. **Never touched:** a text on a **locked layer** (or any record that is not "Update") gets no spot to go to and is never moved; a text **placed by hand** (marked when the drafter moved it themselves) or moved by hand in this same command is left alone with no line; **Xrefs** are only read as obstacles; the tidy writes nothing to an Xref or a REFEDIT object; the pipe itself is never moved. A pipe on a locked layer cannot have its record rewritten: the whole pass is then abandoned with one line ("Text tidy-up after the move was skipped"), as before.
5. **Can it loop or move a text twice per MOVE?** No. One run per command end; each pipe is planned once and written once; the run does not call itself. A text moved to a clear spot is no longer on its strip, so the next MOVE leaves it.
6. **Undo and Redo:** the tidy runs inside the MOVE's own command end, in the same Undo step (the code's own words: "this is still trackedCommand's own end, so record saves are written here"; the baseline notes the command-end rule drops writes at U, UNDO, REDO and MREDO). So **one U takes back the MOVE and the text the tidy moved together**, and nothing new runs between U and REDO. Read from the code; not seen in AutoCAD.
7. **Can it make a pit MOVE slower on a big drawing?** Barely: the extra work is one turned copy per CE text on the moved pit's pipes (a handful), and the drawing scan it shares is the one #1980 speeds up. Not measured.
8. **The "no clear spot" line:** when a text is on its own strip and no spot is clear, CE leaves it and prints "[CE Civil] <pipe text words>: no clear spot ..." on the command line after the MOVE. **It cannot appear for a text the drafter placed by hand** (left silently). It CAN appear for a text on a locked layer (new noise after each MOVE, never a block), and for a pipe label the drafter picked onto the pipe when drawing it with manual placement (that is not marked "by hand"; such a label is also MOVED off the pipe when a clear spot exists).
9. **The main risk, not provable without AutoCAD:** CE draws its pipe label with its bottom edge 125 mm beyond the pipe edge and its invert texts 70 mm beyond (I read the placement code), so a normal label should measure clear. If AutoCAD's extents of a masked text include the mask border, normal labels could measure closer than they look and be moved. The robot's "nothing else moved" case decides this.
