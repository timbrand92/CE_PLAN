### PR #1940: BUG-1144, damaged saved outlet roles in Redesign Apply

1. **What the drafter sees.** Old: if the "outlet roles" record CE saves at each redesign Apply was damaged, the outlet check was skipped silently and Apply wrote over the record. New: Apply completes and the "Redesign applied" message gains one warning line naming `OUTLET_ROLES_DAMAGED_COPY`; the same line goes to the CE log (`Services/NetworkRedesignApplyCoordinator.cs` 227-238). Before the new roles are written, the damaged record's data is copied to `OUTLET_ROLES_DAMAGED_COPY` in the same `CE_CVL_NETWORK_REDESIGN` dictionary (`Services/NetworkRedesignOutletRoleService.cs` 97-133, called at 240 just before the overwrite). A drawing never through Apply is unchanged (status Missing, 41-56). The reader now says Missing / Readable / Damaged (`ReadWithStatusInTransaction`, 31-91); the old `ReadInTransaction` is a thin wrapper with the same answers.
2. **Against the carpark and the decisions.** The carpark asked for a block. R-27 (only two hard blocks: delete spine IDs, push an update on a failed build) overrides it, and CE 04 ruled warn-and-keep-copy on 31 Oct. I found no Tim answer on BUG-1144 in `decisions/2026-10-29_TIM_ANSWERS.md`, so this is CE 04's ruling within R-27, not Tim's word. That is fine because it only softens a stop into a warning.
3. **Switches.** `linking.redesignApplyNoticesDamagedOutletRoles` ON (`Models/UserSettings.cs` 719); `linking.redesignApplyStopsOnDamagedOutletRoles` OFF (727). Both are pinned through `DeserializeSettings` and `DeserializeSettingsTolerant` for `{}` and a group without the keys (`Bug1144DamagedOutletRolesTests.cs` 57-68). A missing settings group reads notice ON, stop OFF (`Rules/RedesignOutletRecordRule.cs` 32-35). **OFF restores the old behaviour exactly:** `Decide` returns None (45-48), no warning is added, `KeepDamagedOutletRolesCopy` is false (`NetworkRedesignApplyTicketService.cs` 212), so the write is byte-for-byte the old path and the message is unchanged. No engineering value is hard-coded.
4. **No-hard-blocks.** No new stop by default. The stop exists only behind the opt-in switch. Two pre-existing stops remain and are not new: (a) Apply refuses while REFEDIT is active (coordinator 47 and 87), which is the native-protection rule; (b) if the damaged shape is a wrong-type dictionary or a wrong-type record, the reader says Damaged and the ticket warns, but `PreflightInTransaction` (`NetworkRedesignOutletRoleService.cs` 152 and 160) still throws and Apply rolls back with "Nothing was applied" (coordinator 261-274). So for those two damage shapes the default is still, in effect, a stop. That was true before this PR; record it so nobody believes "carry on" covers every damaged record.
5. **CE 01's question, answered: where the copy goes.** `OUTLET_ROLES_DAMAGED_COPY` is an Xrecord (a hidden data record, not a drawing object) inside the active drawing's own named-object dictionary, under `CE_CVL_NETWORK_REDESIGN`, beside `OUTLET_ROLES` (`NetworkRedesignOutletRoleService.cs` 107-124). It has no layer, so a locked layer cannot apply. It is written to the database of the document being applied, never to an Xref's database. Apply is refused while REFEDIT is active (coordinator 47, re-checked under the document lock at 87), so it cannot land in a reference edit's working set. The copy step itself creates, moves or erases no entity. (The rest of Apply still writes pits, pipes and the schedule as before; that is unchanged by this PR.)
6. **REDO-safety (BUG-861).** One extra Xrecord written inside the existing Apply transaction, so one Undo removes both; no new command, regen, view or system-variable change.
7. **Things to fix or note.**
   1. **REGRESSION_LOG.md 12-13: the line "8. **Undo:** revert this commit." is doubled, and there is no blank line before the next "##" heading.** The n7 report says this was fixed before commit; it was not. It also carries into #1943 (its lines 25-26). Fix before merge.
   2. **The warning claims a copy that may not exist.** `DamagedWarning` (`RedesignOutletRecordRule.cs` 42-43) always says "CE kept a copy". No copy is made when the record's data is empty (`KeepDamagedCopy` returns at 104), or when the copy fails (caught and only logged, 126-131). Suggest the warning name the copy only when it was made, or say "CE tried to keep a copy". Small.
   3. A second damaged Apply overwrites the earlier `OUTLET_ROLES_DAMAGED_COPY`; only the latest damage is kept. Acceptable; note it in the card.
   4. The warning appears only after Apply, in the result message, not in the preview before Apply. Under R-27 that is acceptable.
   5. `Models/UserSettings.cs` 728-729: a double blank line after the stop switch. Cosmetic.
8. **Tests.** The four new ticket cases (`NetworkRedesignApplyTicketServiceTests.cs`, Bug1144_* at about 122-183) are real behaviour tests on the Apply ticket and would fail on the old code. They pin: default warns once, no stop and the same ticket hash; stop switch ON blocks with one line; notice OFF equals the old answer; no record unchanged; and a readable but mismatched record still gives the old mismatch line. **But the "damaged" fact is set by hand** (`outletRoleDamaged: true`). Two things are only checked by reading the source text (`Bug1144DamagedOutletRolesTests.cs` 88-100): whether a real record with bad text reads as Damaged, and whether the copy really lands in the drawing. That test proves the copy call sits before the overwrite, not that it works. `%APPDATA%`: every Drainage test runs under `SettingsIsolationSetup` (temporary settings file and log folder). The n7 author found none of the new key names in the real `CD_Settings.json`. I did not open the real file.
9. **Not proven, robot (CE 02) and Codex.** N121: on a test copy that has been through one Apply, replace `OUTLET_ROLES` text with `xx`, run the redesign and Apply. Expect: Apply completes; the warning line under "Redesign applied"; `OUTLET_ROLES_DAMAGED_COPY` holds `xx`; `OUTLET_ROLES` is valid again; one U removes both records and the redesign; REDO puts them back. Control A: notice switch OFF, so there is no warning and no copy. Control B: stop switch ON, so Apply refuses with the plain line and the drawing is unchanged. Codex look: the result message wording and its length on screen. (The n7 report's section 5 still describes the first "stop" version; use this scenario instead.)
10. **Verdict: KEEP-WITH-NOTE.** Fix 7.1 (doubled log line) and 7.2 (warning wording) before merge. **Train: FULL**, because it adds a drawing write inside the Redesign Apply transaction and changes the shared Apply ticket.

### PR #1943: BUG-1153, unreadable CDLPD record in Redesign Apply (stacked on #1940)

The reader keeps the old read (so its log line stays). When that read fails, it asks for the reason once more. Only Unknown and UnsupportedVersion count as unreadable (`Services/NetworkRedesignCurrentDrawingReader.cs` 878-895). No CDLPD at all (NoAuthority) and several complete outlets (MultipleOutlets) are unchanged. The ticket adds the line in an `else` after the existing `if (lpd != null)` Fixed checks (`NetworkRedesignApplyTicketService.cs` 849 and 891-906). I checked that a failed read always gives no LPD data (`LpdService.ReadCompatibility.cs`, `IsComplete` and the null data on every failure), so the `else` is reached in every unreadable case.
2. **Against the carpark.** The carpark asked for a block; R-27 makes it a warning, the same as #1940. The carpark marks this bug UNSURE ("the pit may still be protected another way"). A warning suits that.

Both are pinned through both start-up reads, and the #1144 defaults are re-pinned alongside (`Bug1153UnreadableLpdTests.cs` 50-63). OFF restores the old behaviour exactly: `Decide` returns None and nothing is added. One difference with OFF: the extra reason read still runs, but it only reads and changes nothing. No engineering value is hard-coded.
4. **No-hard-blocks.** No new stop by default; the stop is opt-in only.
5. **Native protection and REDO.** Reads only, inside the existing read transaction. No write, regen, view or system variable. Nothing touches layers, Xrefs or REFEDIT.
6. **Notes.**

   2. Drawings with several complete outlets still skip the Fixed check silently. The n7 report leaves that as a question for CE 05. It should go to the carpark as its own item, not be forgotten.

The reader test (`Bug1153UnreadableLpdTests.cs` 85-95) only reads 600 characters of source text, so it is a guard, not proof of what a real conflicting record reads as. Isolation is the same as #1940.

### PR #1945: BUG-1158, CDDESIGN warns when outlets were approved under another file path

1. **What the drafter sees.** When CDLPD approves Design outlets, CE also writes the drawing's full file path into a new record `DESIGN_APPROVED_PATH` beside `AUTHORITY_SET` (`Services/LpdService.cs` 244 and 251-275, in CDLPD's own transaction, `Commands/LpdCommand.cs` around 362). When CDDESIGN loads approved outlets and the recorded path differs from the drawing's current path, it prints one command-line line and carries on (`Commands/CivilDesignCommand.cs` 109-116). The outlets are never un-approved. A drawing approved before this build never warns.
2. **Against the carpark.** The carpark said "outlets show as not yet approved". CE 04 chose "warn, do not un-approve", which R-27 requires anyway. There is no Tim answer on BUG-1158 in the 29 Oct decisions file. The warn-only choice is consistent with R-27; whether the path comparison is the right test is Tim's call (FOR TIM item 4).
3. **Switch.** `linking.lpdWarnsWhenOutletsApprovedInAnotherFile` ON (`UserSettings.cs` 718), pinned through both start-up reads (`Bug1158SaveAsCopyWarningTests.cs` 44-51). With OFF, no path is recorded and no warning appears: the old behaviour exactly. A path recorded while it was ON stays in the drawing, but nothing reads it. No engineering value.
4. **No-hard-blocks.** None. A failure to record the path is logged and ignored (`LpdService.cs` 271-274).
5. **Native protection and REDO.** It writes one more Xrecord in the drawing's own `CE_CVL_SUITE_LPD` dictionary, inside the existing CDLPD approval transaction, so one Undo removes it. CDDESIGN only reads and prints a line. No entity, layer, Xref or REFEDIT involvement; no regen, view or system-variable change. I checked that the existing LPD authority reader looks up its records by name, not by counting the dictionary (`MultiLpdDrawingAuthorityReader.cs` 233-270), and that `ClearLpdData` empty-dictionary clean-up (`LpdService.cs` about 344) is only reached when there is no `AUTHORITY_SET`. So the new sibling record does not make approved drawings read as damaged.
6. **Change needed (small).**
   1. **An unsaved drawing can record the template's path.** `PathToRecord(db.Filename)` (`LpdService.cs` 257; `Rules/LpdSaveAsCopyRule.cs` 33-34) records any rooted path. As far as I know, AutoCAD's `Database.Filename` for a new, never-saved drawing returns the template it was started from (for example `...\Template\CE.dwt`), not "Drawing1.dwg". **I could not check this in AutoCAD.** If it is right, approving outlets before the first save records the template path. CDDESIGN then warns every time, until the outlets are approved again. Fix: record nothing when the drawing has never been saved (read the DWGTITLED system variable, which is a read only), or when the path ends in `.dwt`. The test at `Bug1158SaveAsCopyWarningTests.cs` 37 pins "Drawing1.dwg", which is the assumption in question. Replace it with a `.dwt` case.
   2. **The warning does not say how to clear it.** Add "approve the outlets again in CDLPD to clear this warning" to `LpdSaveAsCopyRule.Warning` (21-22).
7. **For Tim (FOR TIM item 4).** A full-path comparison warns for any colleague who opens the job from a different path, for example a OneDrive folder carrying their user name, a mapped drive letter or a server name. It also warns on every Save As stage drawing (a normal CE workflow: decision 48, BUG-1148) until the outlets are re-approved there. Recommendation: compare the drawing name plus its folder name only. Not a blocker for the code fix above.
8. **Tests.** The path-rule tests (`Bug1158SaveAsCopyWarningTests.cs` 27-41) are real: case, dotted paths, empty sides. The source guard (69-89) proves the path write follows the authority write and the warning follows the load. Its "Does.Not.Contain MarkOutletsUnreadable / BlockLpd" check looks for names that do not exist anywhere, so it guards nothing. Nothing tests the CDDESIGN line or the record in a real drawing. Isolation is the same as above.
9. **Not proven, robot and Codex.** N123: in a saved test copy, approve Design outlets with CDLPD, save, then Save As a new name and run CDDESIGN. Expect the outlets as before plus the one "[CE] Warning: the approved outlets ..." line. Run CDDESIGN in the original file: no warning. Control: switch OFF, no warning. Extra case after fix 6.1: start a new drawing from the CE template, approve outlets before saving, save, run CDDESIGN: no warning. Also U after the CDLPD approval removes `DESIGN_APPROVED_PATH` with the outlets.
10. **Verdict: CHANGE-NEEDED.** Make fix 6.1 (never record a template or unsaved path) and update its test; fix 6.2 is a wording add. **Train: area plus smoke** (Civil CDLPD and CDDESIGN).

### PR #1944: BUG-296, pit rebuild position match in the drawing's own units

1. **What the drafter sees.** When CE rebuilds its pit record (for example after pits were erased and re-made, then a sync), a pit whose id and handle both changed gets its saved lid, remarks, schedule tick and levels back from "a saved pit within 200 mm". In a metre drawing that read 200 m; it now reads 0.2 m (`Rules/RecoveryPositionMatchRule.cs` 17 and 33-34, through the one units conversion `LinkService.ReachMmToDrawingUnits`, `LinkService.PitOutline.cs` 66). The live path passes the drawing's units in (`Services/ProjectDataService.cs` 679, then `ProjectDataService.Recovery.cs` 794-796 and `ProjectDataRecoveryGuardService.cs` 110-118). Millimetre and unitless drawings stay exactly 200. This matches the carpark leftover "the recovery 200 mm matches".
2. **Switch.** `linking.recoveryPositionMatchReadsDrawingUnits` ON (`UserSettings.cs` 718), pinned through both start-up reads for an empty file, an empty group and an older group; a typed OFF is kept (`Bug296RecoveryPositionUnitsTests.cs` 47-62). OFF gives exactly 200 drawing units, the old reading. **R-00:** the 200 mm reach (`ReachMm`) is an internal matching distance, not an engineering design value, so leaving it out of Settings is consistent with BUG-270's other reaches.
3. **No-hard-blocks.** None.
4. **Native protection and REDO.** It only changes a search distance in memory. No new write, regen, view or system variable. The existing save of the pit record after a restore is unchanged.
5. **Notes.** `ProjectDataService.Recovery.cs` 830: the new comment is glued onto the old one ("... drawing's units. mm — wider than reconcile (50mm) ..."). Tidy it. A second, test-only copy of the restore (`ProjectDataService.Recovery.cs` 814-822) still means unitless; no live caller uses it (I searched). The duplicate restore code is older than this PR.
6. **Tests.** Real behaviour tests through `RestorePitUserData`. A metre drawing with a new pit 5 m from the saved one does not take its data with the switch ON (would have failed on the old code), and does with OFF. A pit 0.1 m away still gets its data. Millimetre drawings at 150 and 250 mm give the same answer ON and OFF. The old three-argument call still means 200. The test swaps `SettingsService.Current.Linking` and restores it in `finally`. It is marked NonParallelizable and runs inside `SettingsIsolationSetup`, so it never touches `%APPDATA%`. The live one-line wiring at `ProjectDataService.cs` 679 is not covered by a test.
7. **Not proven, robot.** N12_rec_metre: in a metre-unit test copy (UNITS Metres) with pits P1 and P2 5 m apart and "KEEP ME" in P2's remarks, erase and re-make P1 so its id and handle change, run CDSYNC. 8. **Verdict: KEEP-WITH-NOTE** (comment tidy only). **Train: area plus smoke.**
