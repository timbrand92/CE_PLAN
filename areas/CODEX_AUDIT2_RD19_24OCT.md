1. **ANSWER FIRST — HIGH 0 / MEDIUM 3 / LOW 0.** Three new findings, all SURE by reading the nominated source. No AutoCAD reproduction or speed measurement was performed. These are faults to fix and prove, not new release-blocking rules.

2. **Most important — Civil can hold up AutoCAD while preparing the weekly time report.** Startup reads every time-log CSV, including old months, and can write the office export before loading continues. A slow office folder therefore holds up the drawing window even when the drawing has no CE content.

3. **Second — turning off Structural's background refresh does not stop its startup refresh.** An old or missing schedule-history cache starts the work anyway. The drafter can untick the setting and still get the same unwanted folder reading next time AutoCAD starts.

4. **Third — reopening an old Structural drawing can leave its labels unlinked.** Open it once, close without saving, then reopen it in the same AutoCAD session: CE remembers the discarded conversion and skips doing it again. Moving the old object can leave its label behind.

4. **Numbered findings, ranked.**

   **RD19-01 — MEDIUM — SURE, verified-by-reading: weekly time export blocks the startup thread.**

   **File:line:** `Modules/Drainage/PluginInitialization.cs:216`; `Modules/Drainage/Services/CivilJobTimeService.cs:33-40`; `Modules/Drainage/Services/JobTimeWeeklyExportService.cs:34-50`, `:81-97`, `:115-121`, `:137-158`.

   **What a drafter sees:** AutoCAD is still loading while CE prepares an office time report. This cost applies even to a blank millimetre drawing. A folder with years of time sheets, or a cloud-only CSV awaiting download, can make opening AutoCAD feel stuck before drafting begins. The duration on Tim's PC is unknown.

   **Exact failure scenario and proof:** No recent export marker exists, and the configured `JobTime.DataFolderPath` contains monthly CSV files. `PluginInitialization.Initialize` calls `CivilJobTimeService.Initialize` synchronously. Despite its line 34 comment saying "non-blocking", line 35 calls the whole export directly. The reader enumerates every `*.csv` and calls `File.ReadAllLines` before filtering rows by date. CSV generation, local output and office mirroring also finish before that call returns. Document-event subscriptions and the `CivilJobTimeService initialized` log line come afterwards. There is no task handoff or drawing-content gate on this path.

   **Repeated empty-result case:** With only older rows and none in the requested week, the reader still opens all CSVs. It returns an empty output path, so no completion marker is written. Restarting AutoCAD in the same week repeats the same scan. This is an additional exposure of the same startup work, not a separate counted finding.

   **Smallest fix:** Capture the required settings and paths on the AutoCAD thread, then perform the export's file reads, aggregation and writes on one background task using that detached data. Do not move the live tracker, Settings mutations or AutoCAD objects to the worker. Filtering candidate monthly files before reading them reduces unnecessary work; a successful empty-period check can also be remembered without treating a failed read as success.

   **DETERMINISTIC TEST — fixture:** Isolated test profile; `JobTime.DataFolderPath` points to a synthetic local folder. Under `Time Logs\users`, provide `AUDITOR_2020-01.csv` with old valid rows and one current-month CSV containing a 30-minute row dated in the previous completed week. Leave the export marker absent. All identifying CSV fields are blank or synthetic. Use a fresh empty INSUNITS 4 drawing. Keep office mirroring confined to the test folder or unavailable.

   **Typed steps and assertion:** The native test harness records the thread at entry to `PluginInitialization.Initialize`, and records each weekly-export file-read thread using passive test instrumentation. Start AutoCAD on the empty drawing, let Civil finish loading, then type `(princ "\nRD19-01 READY")`. Require a test CE-log line `RD19-01 export-reads-on-startup-thread=0`, and verify the export totals 0:30. Current source necessarily records a nonzero count: the caller and file reads are on the same thread. This proves the blocking path without a machine-dependent stopwatch threshold. A stronger harness holds the export file-read operation on a releasable latch: READY must appear before release; the export must complete after release. The runner releases the latch in a finally block.

   **Empty-result control:** Repeat in two fresh sessions with only the old-month file. The current implementation emits `JobTime weekly export: no data for ... — nothing written.` before `CivilJobTimeService initialized` in both sessions and reads the old file each time. Preserve this evidence separately from the primary thread assertion. The inspected unit test `Modules/Drainage.Tests/Services/JobTimeWeeklyExportServiceTests.cs:119-136` calls the export directly with in-range data; it does not drive plugin startup or establish which thread owns the work.

5. **RD19-02 — MEDIUM — SURE, verified-by-reading: Structural starts schedule-history refresh with its switch OFF.**

   **File:line:** `Modules/Structural/Plugin.cs:152`; `Modules/Structural/Services/XclmTxtCorpusIndexService.cs:32-56`, `:68-106`, `:239-254`, `:323-324`; setting `Modules/Structural/Models/UserSettings.cs:1113`; UI `Modules/Structural/UI/Dialogs/CeSettingsDialog.xaml:633`, `:731`, `:761` and `.xaml.cs:222`, `:431`.

   **What a drafter sees:** In CESETTINGS, untick **Schedules / Markup > Schedule reading > Background refresh enabled**, save and restart. CE still refreshes its schedule-history data if it is old or missing, even when opening an empty drawing and never using XCLMTXT. The office folders can be read and files downloaded despite the drafter's choice to stop that background work.

   **Exact failure scenario and proof:** Set `XclmTxt.BackgroundRefreshEnabled=false`; provide a missing cache or a non-DWG cache older than 12 hours. Plugin startup unconditionally calls `XclmTxtCorpusIndexService.Initialize`. That method loads the cache and unconditionally calls `RequestRefreshIfStale`. The latter tests only cache source/age, then `RequestRefresh` writes the refreshing state and starts `Task.Run(RefreshCore)`. `RefreshCore` scans configured roots and saves `LastCorpusRefreshUtc`. None of these methods reads the switch. `XclmTxtService.cs:30-34` reads it only after calling the same initializer, so that command-side check cannot protect first initialization either.

   **Thread distinction:** Folder scanning in `RefreshCore` is on a worker; it is not claimed to block the main thread directly. Initial cache loading and the pre-task `SaveCache` are synchronous. The proved defect is that OFF does not stop the automatic work; the resulting amount of lag is unmeasured. A fresh DWG-authoritative cache correctly bypasses this refresh and is not a failing fixture.

   **Smallest fix:** Honour `BackgroundRefreshEnabled` at the common automatic-refresh entry point before changing refresh state, writing the cache or scheduling work. Keep explicit user-requested refresh separate. Also avoid eagerly loading a large optional history cache during startup when that feature is disabled; do not change the office's engineering numbers.

   **DETERMINISTIC TEST — fixture:** Separate test profile with the switch false, a nonempty `CorpusRoots` list pointing to one empty synthetic folder, and both current and legacy `XclmTxtCorpus.json` caches absent. `LastCorpusRefreshUtc` starts empty. This small fixture is sufficient; no office documents are needed. A test-only passive witness counts entries to `RefreshCore` and captures whether `_refreshTask` was scheduled as initialization returns.

   **Typed steps and assertion:** Start AutoCAD with a blank millimetre drawing. Do not run XCLMTXT. Type `CESETTINGS`, select **Schedules / Markup**, then **Schedule reading**; assert the **Background refresh enabled** box remains unticked. The witness must print a command-line or CE-log line `RD19-02 automatic-refresh-starts=0 switch=False`; there must be no scheduled refresh task and `LastCorpusRefreshUtc` must remain empty. Current source schedules one task and, after that task completes, fills the refresh timestamp even though the box is unticked. Do not use a fixed sleep as proof of no task: inspect the captured scheduling decision. Positive control: a fresh process with the switch true and the same absent caches schedules exactly one refresh. Restore the isolated fixture between runs.

6. **RD19-03 — MEDIUM — SURE, verified-by-reading: discarded first-open link conversion is remembered across reopening.**

   **File:line:** `Modules/Structural/Services/LinkMigrationService.cs:22-32`, `:41-56`, `:64-66`, `:76-95`, `:145-172`; consumer behaviour `Modules/Structural/Services/LinkService.cs:7-12`; fixture schema `Modules/Structural/Models/LinkData.cs:7-15`.

   **What a drafter sees:** An older object and its label select and move together on the first open. Close without saving and reopen the same drawing: they no longer select together. Moving the object can leave the label at its old position, although the same file appeared to work moments earlier.

   **Exact failure scenario and proof:** The file contains one valid legacy `CE_STRUC_LINKS/TEXT` pair and no `CE_LINKS_MIGRATED_V2` marker. The first open migrates the pair to a selectable `CE_LINK_...` group and writes the marker into memory. Closing with No discards those changes. However, `InitializedDocuments` is keyed by file name and was populated before the read or migration. It is cleared only by plugin Shutdown; there is no document-close removal. The next open returns at line 65 before reading the unchanged file's missing marker. The modern link implementation relies on the native group, not a legacy follow reactor. A failed first migration is also remembered, but the successful-first-open / Close No case is the clean deterministic reproduction.

   **Smallest fix:** Track the current document/database lifetime instead of a permanent file-name set, remove its entry at document close, and do not mark failed work as complete. Preserve the drawing's saved migration marker as the cross-session authority. No new migration write is needed in an empty drawing.

   **DETERMINISTIC TEST — fixture:** The test lane prepares `RD19_LEGACY.dwg`, INSUNITS 4, with an unlocked line named in the fixture as OBJECT-A from (0,0) to (1000,0), and DBText LABEL-A at (500,200), text height 100 mm. Each carries an extension dictionary `CE_STRUC_LINKS` containing Xrecord `TEXT` with one DXF Text JSON value. Set `ParentHandle` to the line handle and `TextHandle` to the text handle; both dictionaries refer to the same pair. No `CE_LINK_` group or migration marker exists on disk. Save the fixture before loading Structural. Use PICKSTYLE 1 and an independent blank drawing so AutoCAD stays open when the fixture closes.

   **Typed steps and assertion:** Start a fresh AutoCAD session and OPEN the fixture. Require the positive-control log `migrated 1 legacy link pair(s) to groups` and a drawing readback showing one selectable CE_LINK group containing exactly the line and text. Type `CLOSE` and answer **No** to saving. OPEN the same path again. Require that same group and membership again, with a second migration log entry. Current code predicts zero groups, the old JSON still present and no second migration line. For the visible drafting consequence, click OBJECT-A, type `MOVE`, Enter to accept the selected group, base `0,0`, displacement `100,0`; assert line start (100,0) and LABEL-A position (600,200). The failing reopen moves only the line and leaves LABEL-A at (500,200). Discard changes. A separately saved migrated fixture is the control: reopening it must not create a duplicate group.
