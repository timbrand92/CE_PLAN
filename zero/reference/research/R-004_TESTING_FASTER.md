# R-004. Can we test faster? (research, read-only)

**Asked by Tim, 18 Nov 2026:** "is there any way possible to test faster?" **Method:** I read the zero-plan files named in the brief, the office's own probe notes, and Autodesk's and the tool makers' own pages. Nothing was run: AutoCAD and the headless engine were not started, nothing was built or installed, no setting was changed. Where a page refused me (Autodesk's marketing and licensing pages answered "403"), I relied on a search summary of that page and say so. Every claim I could not check on a page I opened is in section 5.

Plain words used here: the **brain** is the sums and checks with no AutoCAD in it; the **hands** read and write the drawing; the **face** is the windows; the **headless engine** is accoreconsole.exe, AutoCAD without a screen.

---

## 1. The short answer

1. **Yes, and most of the saving costs Tim nothing.** The biggest win is moving more of the hands out of AutoCAD (option E) and checking drawn results by reading the saved file with a library (option D). Neither starts AutoCAD, so neither touches the licence or rule 1.9.
2. **Next best: one AutoCAD start that runs hundreds of checks itself (option C),** instead of a robot typing one command per step. The test framework for it (NUnitLite 5.0.0, MIT licence, updated 27 Sep 2026) supports .NET 10.
3. **The headless engine (option A) is faster but is the risky one.** It reads Tim's current profile, needs the plug-in to be trusted, and the office's own note says it cannot start while his AutoCAD is open. It needs Tim's decision before anyone uses it again.
4. **Autodesk's cloud engine (option B) does exist for AutoCAD 2027 and .NET 10,** costs roughly 15 cents a minute (my arithmetic, price unconfirmed), but it cannot read drawings the way our plug-in does and tests no screen behaviour. It is a nice-to-have, not the fix.
5. **Grips, double-click, the ribbon on screen, the Properties palette and "how it feels to drag" will stay slow** (section 3). A second machine (option F) is Tim's licence call, not mine.

---

## 2. The options, ranked by time saved for risk taken

### 1. Option E: a thin "adapter" between the hands and AutoCAD, with a fake drawing behind it

1. **What it is.** The hands logic (which objects to draw, what note goes on each, how a join is stored and repaired, what the self-check on open reports) is written against a small list of plain questions such as "add a polyline here", "read the note on this object", "what does this soft pointer point to". A fake in-memory drawing answers them in tests. The real AutoCAD adapter answers them in the plug-in. Only the adapter is tested in AutoCAD.
2. **What it lets us test.** Everything that is the plug-in's own decision: which notes are written, joins pointing the right way, the self-check wording for each broken case (erased pit, pipe copied alone, exploded pit: trial 1 already found these), the position-stamp comparison (trial 3), what the mover would move. These run in milliseconds, like the brain's 490 tests.
3. **What it will not test.** What AutoCAD actually does to those objects. That is the part trial 1 showed is surprising (the handle in the note going stale after COPY, EXPLODE dropping the extension dictionary, the close-step edit being refused). The fake is only as good as what we have recorded about the real thing.
4. **The honest way to keep the fake truthful:** record real AutoCAD behaviour once, at night, as "golden recordings" (trial 10 already produced one: 123 event lines for a 12-step move, copy, mirror, rotate, undo, redo, erase, scale script that matched between headless and full), and have the fake replay those. Each recording is then re-taken only when something changes.
5. **How much faster.** Unknown as a single figure. What is known: the brain's 490 tests run in seconds; trial 4 measured 40 ms for a real move of one pit on 2500 objects in AutoCAD, so the cost of a test is dominated by starting and driving AutoCAD, not by the logic. How much of the hands moves out depends on how many hand-written decisions versus pure AutoCAD calls it has. My guess, not a measurement, is most of the decisions and a minority of the lines, since the AutoCAD calls are the bulk of the code and the decisions are the bulk of the bugs.
6. **What it needs from Tim.** Nothing. It is a design rule for the build chat: "the hands talk to AutoCAD only through one small interface". The one cost is discipline, because code that reaches straight into AutoCAD objects bypasses it.
7. **Risk.** None to his PC, licence or data. The risk is false confidence if the fake drifts from AutoCAD; the golden recordings and the small adapter test in AutoCAD are the guard.
8. **Sources.** Office evidence: `stage4\TRIAL_RESULTS.md` (trials 1, 3, 4, 10); `design\BUILD_APPROACH_DRAFT.md` (three layers). Autodesk's forum position that any code touching the AutoCAD .NET API can only be integration-tested inside AutoCAD, so logic should be split out: https://forums.autodesk.com/t5/net/how-to-create-unit-testing-for-autocad-add-in/td-p/10724527 (found in search, thread not opened; Autodesk-community post, not an Autodesk statement).

### 2. Option D: read the drawn result without AutoCAD (open the saved DWG or DXF with a library)

1. **What it is.** After a test run saves its made-up drawing, a separate small test program opens the file with a library and checks what is in it: layers, colours, polyline vertices, text, block names, and the hidden notes.
2. **Which library can do the job.**
   1. **ACadSharp** (https://github.com/DomCR/ACadSharp, MIT licence). Reads and writes DWG for versions AC1014 to AC1032 (AC1032 is the AutoCAD 2018 to 2027 file format, so it covers our drawings; verified on its README page). Its objects carry an extension dictionary (`XDictionary`, a dictionary object) and old-style extended data (`ExtendedData`); I read the source line for both (https://github.com/DomCR/ACadSharp/blob/master/src/ACadSharp/CadObject.cs). Xrecord entries are read and kept in both the DWG and DXF readers: a pull request merged 13 Oct 2026 (https://github.com/DomCR/ACadSharp/pull/1287) preserves them on a round trip, so the project is active as of last month. NuGet 3.8.35, published 28 Oct 2026, listed for .NET 8, .NET Standard 2.0 and .NET Framework 4.8, and marked compatible with .NET 10 (https://www.nuget.org/packages/ACadSharp).
   2. **Known weak spot, directly relevant to us:** third-party comparison tests report that ACadSharp lists the handle-valued entries of an xrecord (group codes 330 to 369, which is how a soft pointer is stored) after the other entries, so a reader must find a pointer by its group code, not by its position (https://github.com/libviprs/acadsharp-rs-tests/issues/136; secondary source, a rival project's test list). The same pull request (#1189) says AutoCAD 2027 refused a drawing whose xrecord order had been changed, so **never use ACadSharp to write back a drawing AutoCAD will open; use it only to read.**
   3. **netDxf** (MIT): reads and writes DXF only as far as its page says, no DWG, and the repository was archived on 11 Oct 2023 (https://github.com/haplokuon/netDxf). Not recommended.
   4. **ODA File Converter** (already on this PC, version 27.1.0 in `C:\Program Files\ODA\ODAFileConverter 27.1.0`). It converts DWG to DXF (or another DWG version), with a source folder, target folder, output version, recursive and audit options (https://www.opendesign.com/guestfiles/oda_file_converter). The DXF it writes would be plain text that any parser can read. **Not verified:** whether it keeps extension dictionaries and xrecords in the DXF (DXF can carry both, but I found no ODA statement), and its licence terms (the pages I could open give none; the 60-day trial wording is about the ODA toolkits, not this converter). Read the licence text that comes with the installer before relying on it. I did not run it.
3. **What it lets us test.** The drawn output after a run, without trusting AutoCAD's own read-back: every pipe has the expected vertices and layer, every note has the expected values, every soft pointer resolves to an object that exists, no stray objects. It also makes the "no plug-in" check (trial 3) repeatable: compare a saved sheet with a stored good one.
4. **What it will not test.** How AutoCAD draws or plots it (colours as displayed, line weights, text fitting), grips, behaviour during a command, undo. A saved file is the end state only.
5. **How much faster.** It removes the need for AutoCAD to read results back, and lets a result file be checked on any machine, any hour. Reading one drawing with a library is typically a fraction of a second, but I have no measured figure for our files: unknown. Do not claim a number until one real drawing has been read.
6. **What it needs from Tim.** Nothing for ACadSharp (a free library; the build chat adds it to the test project only, never to the plug-in). A "yes" is not needed for ODA File Converter either, but its licence should be read first.
7. **Risk.** None to his PC, licence or data, provided it only opens copies under the test folder. One caution: the test must never write a DWG with ACadSharp that Tim might open.

### 3. Option C: one AutoCAD start that runs hundreds of tests itself

1. **What it is.** The test project is loaded into AutoCAD once. One test command runs every database-level test against side databases (`new Database()`, or `ReadDwgFile` on a test copy), writes a results file, and finishes. Instead of a robot sending one command and reading one result about sixty times (trial 1 needed about 60 steps), AutoCAD does the sixty steps in one go.
2. **What it lets us test.** Anything that does not need a screen or a pointing device: writing and reading notes and records on real AutoCAD objects, copying objects between databases (the clipboard and WBLOCK route in trial 1), undo and redo inside a transaction, EXPLODE, BLOCK and INSERT, save to older formats and read back, the overrules and events if driven by code. The side-database route is the one our trials used already for notes and records.
3. **What it will not test.** The same list as every non-screen route: selection by pointing, grips, palettes, ribbon, Idle events in the headless engine, real command interaction with prompts.
4. **Existing harnesses (checked).**
   1. **NUnitLite 5.0.0** (MIT, updated 27 Sep 2026) has builds for .NET 8, .NET 10 and .NET Framework 4.6.2 (https://www.nuget.org/packages/NUnitLite). It is small enough to be hosted inside a plug-in's own command. This is my recommended route because it needs no third-party AutoCAD glue.
   2. **CADtest** (https://github.com/AHepker-HOB/CADtest, a fork of CADbloke/CADtest) shows how to run NUnitLite 3 inside AutoCAD or the headless engine. It is a how-to example, targets AutoCAD 2016 and .NET 4.5, has no releases and no stated maintenance. Useful to read, not to adopt.
   3. **RevitDevTool** (https://github.com/trgiangv/RevitDevTool, MIT) lists AutoCAD 2022 to 2027 and runs NUnit, TUnit and MSTest "inside a real" session. Its older package `RevitDevTool.NUnit` is marked deprecated and unmaintained (updated 17 Aug 2026) with the TestAdapter named as its replacement (https://www.nuget.org/packages/RevitDevTool.NUnit). It is young (about 970 commits, 15 stars), it is a development tool whose own page says geometry preview is not supported for AutoCAD, and it does not say it supports .NET 10. I could not confirm that it works with AutoCAD 2027 or without a UI on the screen. **Treat as unproven; do not adopt without a trial.**
   4. **No xUnit runner inside AutoCAD was found.** (A search summary found only forum posts saying people unit-test their non-AutoCAD code with xUnit.)
5. **How much faster.** Unknown until one is built; it saves the robot's per-step wait and the check for stray windows before each send. For the trial 1 pattern (about 60 steps, one check per step) I would expect minutes rather than an evening, but I have no measurement. The trials' own figure for the plug-in work is milliseconds per step; the rest is driver overhead (the office's driver notes about one second per call).
6. **What it needs from Tim.** Normal AutoCAD night hours (5:30 pm to 8:30 am) and a normal start. Loading the test DLL needs NETLOAD, which is subject to SECURELOAD (see option A, item 5). The trials loaded the trial plug-in by hand under Tim's own profile, so the same route works; the note about the SECURELOAD value in his profile is in `TRIAL_RESULTS.md` (trial 10, item 4.3), and it says he is looking at it himself.
7. **Risk.** Same as any full-AutoCAD run on his PC: his own CE plug-ins load too (the trials never isolated them), so the test command must not touch his live CE log or settings (the 23 Sep 2026 note records that a probe once wrote to the live CE log and rewrote the live telemetry file). The test must write only under `C:\CE_WORK\...`.
8. **One thing to avoid.** Run the test command by typing one command, never a long typed script (the first long script jammed AutoCAD in trial 1).

### 4. Option H: AutoCAD's own start-up cost

1. **What is official.** Command-line switches and environment variables override the Options dialog for that session only and do not change the registry (https://help.autodesk.com/cloudhelp/2027/ENG/AutoCAD-Core/files/GUID-7FDC500C-E04A-432D-A73D-EB1B6C6728B1.htm). `/b` runs a script at start-up, `/t` a template, `/v` a view (same page). From Autodesk's switch references (search summaries; the full table page was refused): `/nologo` hides the logo screen, `/nossm` stops the Sheet Set Manager opening, `/ld` loads an ARX or DBX file (not a .NET assembly), and `/p` names a profile (https://www.autodesk.com/blogs/autocad/start-me-up-autocad-switches-tuesday-tips-with-frank/, not opened).
2. **What it means.** Nothing official makes AutoCAD itself start in a fraction of the time. The practical saving is to start it **once** per night and run everything in that session (options C and G), which the "AutoCAD never idle" rule already points to. `/b` plus `/nologo` shave seconds, not minutes, and I have no measured figure.
3. **Rule 1.9 check.** These switches do not themselves change saved settings per the page above. `/p` does not belong in this list at all: it is the profile switch that rule 1.9 forbids.
4. **What it needs from Tim.** Nothing, except that a shortcut with switches means a new launch route; the office's note says AutoCAD must be launched the Explorer way from a file, not from a shell in a repo folder, so switches would have to be passed through a shortcut file. That is a build-chat detail.
5. **Risk.** Low.

### 5. Option G: faster driving than a vision robot

1. **What it is.** Send commands to a running AutoCAD from a small program rather than reading the screen: the office's own driver already does this by attaching to the running AutoCAD through COM (proven on 2027, about 1 second per call, per the driver note). Alternatives: `Document.SendStringToExecute` from a small test loader; Windows UI Automation or the FlaUI library to find and click windows.
2. **What each can do.**
   1. **Typed commands by COM or by `SendStringToExecute`:** run any complete one-line command, set and read system variables. Autodesk's .NET guide says `SendStringToExecute` is asynchronous: the string is not run until the .NET command that sent it has ended (https://help.autodesk.com/cloudhelp/2026/CSY/OARX-DevGuide-Managed/files/GUID-F4A36181-39FB-4923-A2AF-3333945DB289.htm, via search summary). I found no Autodesk statement on whether COM `SendCommand` waits for the command to finish; forum posts say you must watch the command-ended event or the quiescent state. So a loop must wait for the end event, not assume.
   2. **UI Automation and FlaUI:** good at ordinary Windows controls such as our own WPF windows (this is what the face runner already does). I found **nothing** saying they work on AutoCAD's ribbon or drawing area; AutoCAD's ribbon is Autodesk's own control set. UNVERIFIED for AutoCAD.
3. **What it cannot do.** Grips and drags need a real pointing device (trials 2 and 8 needed the Codex real-mouse robot). Anything that waits on a prompt can wedge AutoCAD (the 3 Oct incident: a bare `LINE` left AutoCAD at a prompt for 15 minutes, COM calls refused, Escape and Alt+F4 ignored).
4. **How much faster.** Relative to a vision robot: unknown. The saving is from skipping screenshots and the stray-window check on every step. It is a modest saving and the office already has the driver.
5. **What it needs from Tim.** Nothing new for COM; it is within today's rules (COM attach never launches AutoCAD).
6. **Risk.** Moderate: a command sent at the wrong moment can leave a prompt open; keep to complete one-line commands.

### 6. Option A: the headless engine (accoreconsole), run the plain way

1. **What it is.** AutoCAD without its screen. `AcCoreConsole.exe /i drawing.dwg /s script.scr`. Autodesk's page lists the switches (`/i`, `/s`, `/product`, `/l`, `/isolate`, `/readonly`, `/p`, `/loadmodule`), says commands that open a dialog or palette are unavailable, says applications must not reference AcMgd.dll (it could crash the console), and that WPF and MFC dialogs are not accessible (https://help.autodesk.com/cloudhelp/2026/ENU/AutoCAD-Core-Console/files/AUTOCAD_CORE_CONSOLE.html).
2. **What it can test.** The hands: scripted MOVE, COPY, MIRROR, ROTATE, ERASE, SCALE, UNDO and REDO gave the same events, the same overrule calls for MOVE and the same final drawing as full AutoCAD (trial 10, with the exceptions below). Saves and reopens; notes and records; side databases.
3. **What it cannot test.** No grips, no selection by pointing or by window (trial 10: window and crossing found "0"), no palettes, no ribbon, no WPF, no Idle event (it fired 0 times in both runs), no live preview. The overrule "close" call fires less often than in full AutoCAD (65 against 83 in trial 10), so never count closes. The office's note says the graphics manager is null (reading it twice kills the process).
4. **Does it take a licence, and can it run while his AutoCAD is open?**
   1. **Licence.** Autodesk's page says nothing about licensing. A forum answer from a community member says it is part of AutoCAD and not free (https://forums.autodesk.com/t5/autocad-forum/autocad-core-console/m-p/8104223, not opened, from a search summary). UNVERIFIED by Autodesk. Reports on running several at once conflict: one user ran two at once and got licence errors beyond that, another runs five or more in production (summaries of https://forums.autodesk.com/t5/net/parallelism-for-reading-drawing-data-using-accoreconsole/td-p/6062384, page refused). I found no Autodesk statement either way, and a separate thread reports a licence error from a program that launched it (https://forums.autodesk.com/t5/vba-forum/accoreconsole-exe-license-error/m-p/6849875, title only).
   2. **While full AutoCAD is open.** No Autodesk page says. One forum answer says it can run in parallel with AutoCAD; **the office's own note says on this PC it cannot start while the full AutoCAD is open (a machine-wide lock)**, found September 2026. The local fact wins for this PC. So: not during his working day, and treat it as counting as "AutoCAD" for the 5:30 pm to 8:30 am rule unless Tim says otherwise.
   3. **Parallel runs.** Several can be launched, but see the licence reports above and one forum report that IMPORT hangs when two run at once. Treat parallel runs as unproven on this licence.
5. **The unsigned DLL and the trust question.**
   1. Autodesk's page says applications must be in a trusted location or the console fails to load them (the page's example is AutoLISP; for .NET, the NETLOAD page says secure mode loads only files from trusted locations, https://help.autodesk.com/cloudhelp/2022/ENU/AutoCAD-Customization/files/GUID-D790D6DA-4592-4C58-910F-42E4AA9EA982.htm). The page's way to add a trusted location is the Options dialog, which is a saved setting: **that is a rule 1.9 matter, Tim's explicit yes needed.**
   2. SECURELOAD itself is a saved system variable (registry), default 1 (https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-LT/files/GUID-541566C6-2738-49DD-87C3-C1490E924A02.htm, via search summary). Setting it from a script also changes what is stored: **a rule 1.9 matter.** The first trial run did exactly this and a licence error followed.
   3. **Without `/p`, Autodesk says the console uses the profile most recently used in AutoCAD,** that is Tim's own (same Core Console page). So a plain run reads his profile. According to `TRIAL_RESULTS.md` his profile's SECURELOAD is currently 0, so on that evidence a NETLOAD from a script would not be blocked, but I have not re-read his profile and the cause of the earlier licence error is not proven. Do not rely on this.
   4. **Setting-free ways round it, none verified for the console:** (a) load from a folder already trusted; the Program Files folders are always trusted (search summary of the Autodesk security page), but writing there needs administrator rights and changes the install, so no; (b) sign the test DLL: Autodesk's bundle page says signed files are not warned about (R-002 item I.2, from the 2025 help page) and the office has a release signing key (memory note "Signing key exists"), but using that key for test builds is Tim's decision and whether a self-made certificate satisfies the check is UNVERIFIED; (c) a per-process environment variable or switch for SECURELOAD or TRUSTEDPATHS: **I found none.** The startup page says environment variables override Options values for the session, but I found no variable for these two. One forum thread reports a DLL on a trusted drive still did not load under the console until it was copied into the install folder, and another reports "Unknown command NETLOAD" with SECURELOAD at 0 (search summaries, not opened), so it may not be that simple.
   4. **`/isolate`** is forbidden by rule 1.9 in this project's limits, and Autodesk's page gives its syntax only. In the earlier trials it kept the plug-in's start-up from writing to live files. Without it the console loads whatever bundle is installed for his user (the office's note of 23 Sep: CE_CVL_SUITE start-up wrote to the live log, read the live settings and rewrote the live telemetry file). **A plain run can therefore touch his live CE data.** The headless proof harness in the monorepo (`tools\headless-proof\Run-HeadlessProof.ps1`) sets a unified-host switch to stop that; whether it also avoids `/isolate` was not checked.
6. **Is it a risk to his open session in the working day?** Unknown, and not worth finding out by testing: the local note says it cannot start, and a licence error was seen once. Do not run it while his AutoCAD is open.
7. **How much faster.** Unmeasured. Starting a console is quicker than the full program and there is no window to read, so it is likely to be the fastest route for the hands, but this PC has not given a figure and I will not make one up.
8. **What it needs from Tim.** A decision on three things in words: whether the console counts as "AutoCAD" for the hours rule, how the test DLL may be trusted (signed, or a trusted-path entry), and whether `/isolate` may be used. All three are rule 1.9 or licence-adjacent.
9. **Risk.** The highest of the free options. Touches his profile, may share his licence, may write to his live CE files.

### 7. Option B: Autodesk's cloud engine (Design Automation API for AutoCAD)

1. **What it is.** Autodesk runs AutoCAD's core engine on its servers. We upload our plug-in as an "app bundle" and made-up test drawings; it runs a command or script and returns files (https://aps.autodesk.com/en/docs/design-automation/v3/developers_guide/overview/).
2. **Engine versions.** Yes, **AutoCAD 2027 is there** (engine ID `Autodesk.AutoCAD+26_0`), released 30 Mar 2026, **requires .NET 10**, deprecation 29 Mar 2030, removal 29 Mar 2032. The 2025 and 2026 engines (`25_0`, `25_1`) use .NET 8; the old 2021 engine was removed on 29 Mar 2026 (https://aps.autodesk.com/blog/end-autocad-2021-engine-new-autocad-2027-engine-released). Autodesk's example repository has two .NET 10 bundles for the 2027 engine and a local-test script for each (https://github.com/ADN-DevTech/autocad-automation-apps).
3. **Cost.** Search summaries of Autodesk's APS pages put AutoCAD at **2 Flex tokens per processing hour**, billed by the second, including download and upload time (https://aps.autodesk.com/blog/estimate-design-automation-costs, which gives the older "4 cloud credits per hour" and the billing method; Flex wording from search summary of the current pricing pages). The Australian Flex page, per a search summary, lists A$4.40 per token for small purchases. **My arithmetic: about A$8.80 per processing hour, about 15 cents a minute, so a three-minute job is about 44 cents.** Treat as an estimate: I could not open Autodesk's pricing pages (403) and found no APS-specific dollar price, no confirmation of a free allowance, and no confirmation of any minimum purchase. Tokens expire after a year per the same summary.
4. **Time and parallelism.** Autodesk's limits page: a work item has a default 100 second limit, adjustable to a **maximum of 3,600 seconds** for AutoCAD (an older ADN blog says 900; the limits page is newer and wins), including upload and download; no output for one minute kills it; no concurrency limit is stated on that page; status polling is limited to 150 calls a minute per app; there is no monthly cap unless you set one; the uncompressed bundle may be 500 MB (https://aps.autodesk.com/en/docs/design-automation/v3/developers_guide/rate-limits/da-rate-limits). Queue health is published per engine (https://aps.autodesk.com/node/4029). **Time per job including engine start-up: unknown;** the queue and start-up delay are not on the pages I could read.
5. **What cannot be tested there.** Everything the headless engine cannot (no screen, no WPF, no grips, no palettes, no ribbon; "AutoCAD without a UI"), and in addition: running OPEN or NEW, and `Database.ReadDwgFile` (the ADN blog says use the input-file route instead), plotting layouts the plug-in creates, loading by `LoadOnAutoCADStartup` (use `LoadOnCommandInvocation`), installing anything, and no vertical (Civil 3D) APIs (https://blog.autodesk.io/notes-on-using-da4a/, an older Japanese ADN blog, so check each limit against the 2027 engine before relying on it). Input drawings must be uncorrupted: audit errors or non-TrustedDWG warnings may abort a job.
6. **What Tim would need.** An Autodesk Platform Services account with client credentials (the example repository's scripts "need APS client credentials"), a payment method or Flex tokens, and a decision to put the plug-in and made-up test drawings on Autodesk's servers. Only made-up drawings would be sent; the plug-in bundle itself would be uploaded (the plug-in is the office's work, not client data). The page I opened on required accounts and storage did not cover them (UNVERIFIED beyond the credentials).
7. **Rule 1.9.** None of it touches his profile, licence, sign-in or PC: it runs on Autodesk's machines under the account's own billing. It does not use his AutoCAD seat.
8. **How much faster.** It would not be faster for one test, because every job pays for upload, queue, start-up and download. Its real value is **many tests in parallel, at any hour, with no use of his PC and no rule 1.9 exposure.** Whether that beats option C run at night, on a machine that is already free overnight, is doubtful for the hands tests we have.
9. **Risk.** Money and a new account, privacy only if real drawings were sent (they would not be).

### 8. Option F: a second place to run AutoCAD

1. **What it is.** A virtual machine (Oracle VirtualBox is installed), a second PC, or a cloud desktop, so AutoCAD is not limited to nights on Tim's working PC.
2. **What Autodesk's terms say (information, not advice).** According to a search summary of Autodesk's Terms of Use, subscription types page (effective 7 Feb 2024; I could not open it): an authorised user of a single-user subscription "may install the Software on up to three (3) Electronic Devices, but they may use only one (1) Electronic Device at a time". "Electronic Device" is defined to include computers and "virtual machines not accessed through a network connection". Autodesk's account pages say whether virtual use is allowed depends on the product, how it was bought and the plan's terms, and that only one authorised user can access a single licence at a time. A support article says Autodesk software can be installed and used on multiple computers if only the named user uses it (search summaries of two Autodesk support pages, the account "virtualization" page and the support article on installing on more than one computer; both pages refused me). The General Terms were updated on 30 Mar 2026, newer than the page I saw.
3. **What that means in drafting terms.** One person, up to three installs, one running at a time. **A second AutoCAD running while Tim's own is running looks like the very thing the "one at a time" wording rules out,** so a second machine does not by itself lift the day limit; it would help only if Tim is not using AutoCAD at that moment, which is the same as the night window today. Whether his plan is single-user, and the exact wording for it, is for Tim or Autodesk to confirm.
4. **Practical points.** Autodesk says hardware acceleration is unavailable in a virtual desktop such as Citrix (https://autodesk.com/br/support/technical/article/Hardware-acceleration-is-unavailable-in-AutoCAD-over-Citrix, title and summary only). I found nothing on VirtualBox and AutoCAD 2027 specifically (UNVERIFIED), so expect graphics, real-mouse and screen-look results from a VM to differ from his PC.
5. **What it needs from Tim.** His own reading of the terms for his plan; probably a call to Autodesk; and a second installation signed in under his account.
6. **Risk.** Licence compliance is the main risk. Signing in on another machine can sign him out of the first (Autodesk's sign-out article says to sign out of one machine before using another; summary only). Given the 16 Nov licence incident, I would not try this without Tim's explicit decision.

## 3. What stays slow no matter what

Only a real mouse in full AutoCAD, or Tim's own eyes, can prove these:

1. **Grips.** The custom grip crashed AutoCAD in trial 2. Clicking, dragging and the grip menu need a real pointing device. The built-in grips, the grip-drag copy and the menu were not tested.
2. **Double-click.** Detection worked; stopping AutoCAD's own PEDIT from also opening was not solved (trial 8).
3. **The Properties palette.** Whether the palette shows our rows needs the palette open, which is a saved interface setting (trial 5).
4. **The ribbon tab and tips on screen,** and workspace switches and restarts (trial 7).
5. **How a drag feels with the ghost image.** Trial 4 measured the commands, not the feel.
6. **Pan and zoom by mouse while Inspect has the window hidden** (trial 6) and the window at 2560 x 1440 on a real screen.
7. **The first-run trust prompt and the AutoCAD side of update and rollback** (trial 9): these need a bundle folder and the registrations AutoCAD writes.
8. **Whether it looks right.** Colour, dark theme, text fit, line weights on a real plot. A library can say what is in the file; only a person or a plotted PDF can say it looks right (trial 3 compared PDFs pixel by pixel, which is a good machine check for "looks identical").
9. **Anything on idle,** because the headless engine never fires it (trial 10).
10. **The interaction with Tim's own CE plug-ins** loaded in every full-AutoCAD run so far (unmeasured).

These are about 10 items. The aim of everything above is to make **only these** need a night in AutoCAD, and to batch them into one session using option C and the existing driver.
