## FOR TIM

1. **The honest answer: only 3 bugs are open, buildable and free of a draft, so this tranche has 3 batches, not 12 to 15.** I would not pad it. A builder who starts a bug that already has a draft fix only makes a second copy of the same work.
2. **Why so few:** the carpark has 974 open entries. 562 of them plus about 100 more already have a draft PR (1571 drafts are open). Of the plain "OPEN" entries that are not installed-and-waiting, not in tranche 1 or 2 and not on hold (412), 257 are already in the code on the Civil or Structural line under their number, and 134 have a draft that is not merged yet. That leaves 21, and 18 of those 21 fall away on a closer look (list in EXCLUDED).
3. **The three batches, in drawing terms:**
   1. **t1 BUG-805 X-Civil import reads metres and depth columns properly:** "1.2 m" in a consultant schedule no longer turns into 1.2 mm, a "CL 8.45m 1.20m" row no longer gives a depth of 8450 mm, and a half-blank pipe row does not lend its size to another pipe.
   2. **t2 BUG-872 the Glen Eira back-test goes green:** the test that fails in every build report today (the "known" failure) is brought back in line with the issued sheet. Test only, nothing changes in AutoCAD.
   3. **t3 BUG-300 OOPS after erasing a footing line:** after ERASE then OOPS, CE puts the footing back and redraws its outline straight away, not only at the next footing command. This one starts only after a robot check confirms the gap is real.
4. **What I recommend instead of more builders:** 134 bugs already have a finished draft waiting (numbers in EXCLUDED, item 3). Merging and proving those moves the pilot further than any new batch. The desk, not a builder, owns that.
5. **Order and why:** t1 first (X-Civil import is the one daily-use path left with an open wrong-answer risk), then t2 (no clash, makes every later test report cleaner), then t3 (needs the robot check and is the most REDO-sensitive).
6. **Left out and why:** everything already built or drafted, everything installed and waiting for a proof run, every question waiting for you (BUG-95, 431, 538, the 75/100 mm cover, DIMSCALE for CD label text, minimum fall for 450 mm and bigger, voice batches 7 and 8), BUG-510 and BUG-1006 (both need a number or wording from you), the CEMEMBER cards, hatch card CH, DSET styles, CESETTINGS and installer cards, and anything needing CE_SHARED.

8. **Two PR titles carry the wrong number:** #817 and #829 say "BUG-805 wording" but are about a Pit Schedule typed-level wording, not the X-Civil schedule fault. That is why BUG-805 looked covered. Worth correcting by the desk.
9. **Not tested by anyone:** this is a plan. No code ran and AutoCAD was not opened. "Already on the line" means a commit message carries the bug number, nothing more. I confirmed by reading that BUG-805 part 1 is still in the code (`XcivilVisionScheduleParser.cs` line 161 strips a trailing "m" and keeps the number).
10. **Nothing here needs a decision from you.** t3 has a robot gate; the others can start in the next free window.

## HOW THE LIST WAS MADE (so it can be repeated)

1. **Open entries:** a script took the last line containing the word Status in every entry of `BUG_CARPARK.md` (1217 entries, 974 plain OPEN, none without a Status line).
2. **Removed in turn:** every bug number named in `NEXT_TRANCHE_31OCT.md`, `NEXT_TRANCHE2_01NOV.md` or any `BUGFIX_*_REPORT_*.md`; every entry whose status says "fix installed" or "found by reading code" (waiting for proof, or checked in tranche 2); anything ON HOLD.
3. **Open PRs:** all 1571 (title and branch name searched for a bug number). A PR whose title is only a coverage audit, a test or "regression cases" was not counted as a fix.

5. **Then each survivor was read** in the carpark and, where a file was named, in the code on the line.

## A. THE BATCHES

1. **t1: BUG-805 X-Civil import reads metres and the depth column properly**
   1. **THE TASK:** BATCH t1 of tranche 3. A drafter runs CDIMPORTXCIVIL on a consultant PDF or DWG schedule. Expected: a size or depth written in metres ("0.9 m", "1.2 m") is read as metres and converted to millimetres once; the pit depth comes from the depth column, not from the first "number m" in the row; a pipe-schedule row with one end blank is left unassigned (Unknown), never given to whichever pipe has an unresolved From pit. Actual (carpark BUG-805, three parts): (1) the AI-vision parser reads "1.2 m" as 1.2 mm, so metre sizes fail the existing 300 to 5000 check and the rows are dropped; (2) the DWG schedule reader takes the first "number m" as depth, so "CL 8.45m 1.20m" gives a depth of 8450 mm; (3) a half-blank pipe row hands its diameter to the wrong pipe. Confirm each part on `origin/claude/rel-20261102a` with file and line before building and say which parts are still real (part 1 is, at `Services/XcivilVisionScheduleParser.cs` `GetDoubleField` line 161). Files expected: `Services/XcivilVisionScheduleParser.cs` (line 161), `Services/XcivilScheduleService.cs` (lines 523 to 584 for the GN-ANNO-TABL row and depth pattern; `ApplyPipeScheduleToImportedPipes` near line 1175), `Models/UserSettings.cs` (the XcivilImport group near line 3652), tests under `Modules/Drainage.Tests`. Switch `xcivilImport.scheduleReadsMetresAndDepthColumn`, ON by default, documented "Default: on."; OFF restores today's reading exactly. No new engineering number: reuse the existing 300 to 5000 mm size check and the existing Settings depth range; where the depth column cannot be told apart, leave the depth Unknown and add a plain warning to the import results (R-27, warn and carry on). Before editing, run `gh pr list --state open --search "XcivilScheduleService"` and read #817 and #829 (they carry the label "BUG-805 wording" but are about the Pit Schedule typed-level wording; confirm they do not touch these files). Read the X-Civil import rules in C:\CE_PLAN\areas before starting; import must never touch locked layers, Xref or REFEDIT content.
   2. **Risk:** MEDIUM. A wrong unit is 1000 times wrong; part 2 changes which text is trusted as depth, so test with made-up rows only (no client data, RULES 11). REDO: the import is one undo step today; do not add writes.

3. **t3: BUG-300 OOPS after erasing a footing line puts the footing back at once**
   1. **THE TASK:** BATCH t3 of tranche 3. Gate: CE 02 runs the robot check below first and CE 05 attaches the result; if OOPS already restores the footing and its outline before any other footing command, close the batch as "no change" with the evidence. 5. **The acceptance ledger and `REGRESSION_LOG.md` were not searched line by line.** I read the commit messages for C-78 and C-79 and the known-failure line for BUG-872, nothing else; check them before t1 starts in case C-79b1 touched the import path.
